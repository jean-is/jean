# Decisions

Each entry is a decision as it stands: what was chosen, why, and what was rejected, so it isn't proposed again. Numbers are stable, because code, docs and commits cite them. When a later decision amended an earlier one, both live in one entry under all their numbers, so searching for any `Dnnn` lands on the current rule; git history keeps the original wording. A number heads one entry only: a decision that changed several heads the one it changed most, and the others name it. `test/decisions.test.js` checks that every number cited heads exactly one entry. D124 and D151 were never used.

A new decision takes the next number after the highest one here, checked again just before writing, since several sessions may add numbers at once. It goes into the section it belongs to; if it changes an existing entry, rewrite that entry to the new state and add the number to its heading. A budget is raised only by the owner, in a change of its own.

## Product

- **D1 · Reboot from scratch** rather than refactor DEVS. *Why:* no users or years of fixes to protect; cutting 95% is harder than writing ~5k clean lines. *Rejected:* pruning DEVS ([background.md](background.md)).
- **D2 · First user: a non-technical knowledge worker; one job: files in, things out.** *Why:* a sharp job beats an architecture ("swarm") as a pitch. *Rejected:* developers first; generic chat; a separate mode for code.
- **D5 · Progressive discovery, like a game.** Jean starts as one box; a capability's code loads when it is discovered. *Why:* the simple first screen and the small first load are one decision. *Rejected:* a feature-complete UI from day one.
- **D6 · Discovery is triggered by events, reflexes and the brain's `offer()`, never by keywords.** *Why:* it works in every language. *Rejected:* regex or keyword intent rules.
- **D7 · D224 · D225 · One agent loop, plus helpers, meetings of the projects' assistants, and methods as ready-made skills.** Delegation is one tool (D98). A meeting has the assistants of the room's other projects speak on a topic in rounds, each from its own project and without tools, the room's assistant chairing; it asks first, naming its projects, since a project's memory and tasks are its own ([architecture.md](architecture.md#meetings)). The methods people at work recognise are six ready-made skills, one per kind of work, each picking the method the situation calls for ([product.md](product.md#instructions-and-memory)). *Why:* 2026's winners are single-loop agents; a project with a name and a way of being is what others call an agent, so people ask for their agents to meet, and a standing status meeting is a routine; a method is steps, which is what a skill is. *Rejected:* DEVS's decomposer, standing teams with roles and persona libraries; methodology templates as modes of the loop; speakers with tools (a meeting reads what each project knows, and acting stays the chair's, under the rules); assistants calling meetings among themselves, or rounds without end; a transcript per meeting; each speaker on its own project's brain (one answer mixing keys and providers); a skill per method (a line each in `<skills>`, and tiles nobody can tell apart); a method field in `project.md` (instructions already say it); DEVS's methods for developers (test-driven, behaviour-driven and domain-driven design, XP, the V-model, RAD, Crystal, SAFe, Scrum for software), since the first user doesn't write code (D2); its agent patterns (greeter, operator, orchestrator, listener), the swarm; TQM, a culture rather than steps; Six Sigma beyond DMAIC, its method; YOLO, which is what Jean does without a skill.
- **D27 · D242 · Data is bound to the origin, so the domain is settled before launch: jean.is, bought.** The desktop app's bundle id is its reverse, `is.jean.desktop`. *Why:* changing it means moving everyone's data. *Rejected:* launching on a temporary domain; jean.cx.
- **D38 · D50 · Jean is its own project, in its own repository,** moved out of DEVS with its history (`git subtree split`): nothing read, imported or copied from outside the repository, and no devs.new redirect. *Rejected:* Jean as DEVS's successor; a DEVS subfolder.
- **D3 · D39 · D139 · Open core: MIT, with the enterprise integrations in `ee/` under the Elastic License 2.0 and a key.** Reputation first, money second. Everything a person or a team uses is MIT; `ee/` holds only what an organisation's IT, security or compliance team asks for, never the person's own security, a standard Jean speaks or anything already open, and nothing moves from open to `ee/`. One module loads `ee/` with `import()`, only when policy holds a key, which is checked offline inside `ee/`; `ee/GRANT.md` makes every version MIT if no key can be bought for twelve consecutive months. Keys: [enterprise.md](enterprise.md#open-and-enterprise). *Why:* small players get the whole product, big ones adopt it bottom-up and pay when their IT needs the integrations; Elastic-2.0 is short, on the SPDX list and known to legal teams; Ed25519 would need browsers above D40's floor. *Rejected:* BUSL on everything; AGPL with a commercial licence; FCL (not on the SPDX list); PolyForm Small Business; a custom licence; online key checks; keys that stop a running version; locked features shown in the open version.
- **D45 · D226 · One relay, not built, for what needs browsers to reach each other: live sharing, requests between people's Jeans, and a person's phone driving their Jean (D227).** Hosted by the maintainer on a subdomain of Jean's domain, it runs only once someone turns one of them on, forwards end-to-end-encrypted traffic it can't read, and is self-hosted or switched off by policy (`urls.collaboration`); two Jeans pair through a link whose `#fragment` carries the key. A request from a colleague's Jean arrives in the inbox as a card, read as data and never as instructions, and is answered by the recipient's own brain, keys and rules, only reading unless they allow more (as Since last time does, D101); they approve what goes back. A2A's messages are the likely format. Live sharing is WebRTC between the participants, the relay for signalling, the organisation's TURN server where a network needs one, and Yjs only for shared documents. Secrets never cross. *Why:* a person's agent is their project, on their device; working with colleagues means asking theirs, and each side keeps its keys and its say. *Rejected:* no public relay; a relay that can read content; a Jean server that runs agents; a request run with the sender's authority; one person's brain answering for another.

## Stack and budgets

- **D9 · D43 · D51 · D52 · D74 · D243 · D247 · D318 · No build step, nothing generated or third-party is committed, and what a deploy serves is one folder, `app/`, which a web deploy minifies and compresses.** Jean's own code runs as written, from `app/`; the root holds what never ships (`cli/` with its strings, `gateway/`, `desktop/`, `deploy/`, `scripts/`, `test/`, `docs/`), and `test/` holds both kinds of test, told apart by their names, a capability's two side by side. Third-party runtimes and the generated listings are copied from Jean's own `node_modules` into `app/`, never from a CDN; `npm run build:web` minifies only Jean's own code into `dist/web/`, each file beside itself in brotli and gzip ([architecture.md](architecture.md#stack)). *Why:* the code that runs in development is the code written, and view-source is the source there; on the web, the first load goes from what Caddy compressed on the fly (zstd) to about 40% less, a second on a slow connection, and ONNX Runtime's wasm from 6.2 to 3.8 MB; third-party code in history is noise in every diff; `package-lock.json` makes the copies reproducible; one folder to copy, and a root that shows the project rather than the site. *Rejected:* a Vite or TypeScript build; a bundle for the web (11 KB less on the first load, but each capability bundled with the shell to keep one copy of signals and lit-html, chunk names in place of the paths the service worker, the preloads and the render package know, and the whole shell downloaded at each update, while the preloads already fetch the graph in one round trip); source maps; minifying third-party code (mostly minified already: again, abcjs, ECharts and MapLibre grew); minifying for the browser floor (esbuild turns `\p{…}` regexes into `new RegExp` strings, un-nests `@starting-style` and adds `-webkit-` prefixes); esbuild's other rewrites of style sheets (they round `oklch()` colours to sRGB, for 11 bytes); terser with a CSS minifier (two dependencies for one); zstd copies (brotli at its best is smaller); budgets measured on the minified files (the limits would loosen by a third, undecided); committing `vendor/` or the generated files; runtimes from a CDN; `transformers.min.js` (bundles its own ORT); a monorepo of packages (`packages/core`, `packages/web`…): a browser loads `core/` from the folder it is served from, so a package would be copied in at build, a build step under another name, or reached through `node_modules` links that a copied folder loses, and jean-cli is the app's own modules, which `npm run cli` already puts together; `LICENSE` only in `app/` (forges look for it at the root) or committed twice; inside `app/`, a `pages/` folder (`index.html` and `sw.js` stay at the top, the service worker's scope, and the other pages gain nothing), `brand.js` renamed `config.js` (it is for display only, and Jean's configuration is Settings and policy), and a `public/` or `assets/` folder for the fonts, icons and screenshots (all of `app/` is served, and their addresses would change for two lines fewer); for the tests, one runner (`node --test` drives no browser, and Playwright would bring browsers into `npm run check`), `test/unit/` and `test/e2e/` (every unit test's imports moved, and a capability's two tests apart), or tests beside their modules (`app/` holds what ships).
- **D10 · Custom elements with `@preact/signals-core`, `lit-html` and `marked`'s lexer, the only libraries loaded upfront.** *Why:* standard elements upgrade when their module loads, which *is* progressive discovery, and all of it is CSP-safe. *Rejected:* Preact with htm; VanJS; Alpine (needs `eval`); htmx (needs a server).
- **D66 · QuickJS and Playwright:** `quickjs-emscripten-core` with only the release-sync variant (~600 KB with its wasm), loaded on demand; `@playwright/test` as a dev dependency, run by `npm run e2e` in Chromium and WebKit against the fake brain, apart from `npm run check`. *Rejected:* the `quickjs-emscripten` package with every variant; browsers inside `npm run check`.
- **D37 · Development uses a deterministic fake brain** (`test/fixtures/fake-brain.js`). *Rejected:* testing only against real providers.
- **D62 · Mechanisms live in `core/`, product policy outside it.** `core/decide.js`, `core/deferred.js` and `core/search.js` are mechanisms; which reflex questions are asked (`caps/reflexes/questions.js`) and how Auto picks a brain (`ui/auto.js`) are policy, in pure modules tested under `node --test`. *Why:* `scripts/reflexes.js` imports the same questions, so what is measured is what runs.
- **D75 · Shared types live in `core/types.d.ts`,** which never ships and which `loc.core` doesn't count. *Rejected:* a JSDoc-only `types.js` counted as code.
- **D96 · A module that only one capability, or one part of the UI, uses lives with it,** tested under `node --test` all the same; what several share, such as `core/zip.js`, stays in the core ([architecture.md](architecture.md#layout)). *Why:* the core is the engine you read in an afternoon. *Rejected:* raising `loc.core`.
- **D76 · D94 · D148 · D211 · The first load holds what the first screen draws, and one catalogue.** Everything else, from the dialogs to what a message needs on its way, loads when first needed and stays in the shell's precache for offline use ([architecture.md](architecture.md#stack)); `useLocale()` fetches only the chosen language's catalogue, and the budget counts the largest. *Rejected:* preloading after the first paint; a lexer-only `marked` (its published file can't be tree-shaken).
- **D97 · A language's catalogue comes in parts:** what the first screen and the conversation show, what only dialogs show (`locales/dialogs/<lang>.json`, loaded by `ui/dialogs.js`), and a part of its own (`locales/<id>/<lang>.json`) for a capability whose strings would weigh on the first load ([architecture.md](architecture.md#languages-i18n)). `test/locales.test.js` checks that every string is used, and only where its part is loaded. *Rejected:* trimming sentences; one part per capability for all of them.
- **D86 · D129 · D161 · D171 · D175 · D179 · D186 · D189 · D203 · D204 · D206 · D209 · D213 · D217 · D221 · D231 · D237 · D239 · D256 · D258 · D266 · D272 · D278 · D290 · D297 · D298 · D310 · D314 · D327 · D330 · D335 · D337 · D339 · D342 · The budgets are [budgets.json](../budgets.json)'s, and only the owner raises one, in a change of its own.** The app has 25,681 lines of code, the core 1,900 and jean-cli 800; the first load 105.5 KB, a capability's code 50 KB, a part of a language's catalogue 9.5 KB and the CSS 12 KB, gzipped; the base prompt 200 tokens (D8). A raise comes once a search for lines or bytes to delete found none; `npm run budgets` prints where each stands, and git keeps what each raise was for. *Why:* going over a limit means deleting something first. *Rejected each time:* raising it inside the change that needs it; thinning a shipped capability.
- **D244 · The development server checks the budgets after each change,** says each one over until all are met again, and still serves ([architecture.md](architecture.md#stack)). *Why:* every budget had reached its limit, and `npm run check` comes once a feature is built around the room it took. *Rejected:* refusing to serve while one is over (the shared checkout holds other sessions' unfinished work, and a feature is seen before it is trimmed); checking only as it starts (a development server stays up for hours); importing the check into the server (Node keeps the prompt's module as it first read it).
- **D246 · The line budgets count lines of code,** a line counting when it holds anything but comments and white space, and the limits were set to about the room each had ([architecture.md](architecture.md#stack)). *Why:* a comment explains and a blank line spaces; counting them made a trim condense JSDoc, which carries the types `tsc` checks, as three fifths of the core's trim for D245 did. *Rejected:* cloc or another counter as a dependency; TypeScript's parser (TypeScript 7 is the native compiler, with no JavaScript API); regular expressions over the text, which take `'**/*.js'` or `'https://…'` for a comment; counting JSDoc as code.
- **D240 · D245 · jean-cli keeps to 800 lines of code** (`loc.cli`), reusing the core and the capabilities' pure modules as they are, so what it adds is what a host outside the browser needs, and what both need lives once, where both import it ([architecture.md](architecture.md#layout)). *Why:* `loc.app` counts what a browser loads; 800 once `cli/` copied nothing of the app's. *Rejected:* counting it in `loc.app`; no limit, as `bridge/` and `gateway/` have none.
- **D232 · A container image, for organisations that deploy with containers** (`deploy/docker/`, MIT): nginx's unprivileged image serving what a copy of `app/` serves, with an empty policy the organisation's replaces and a header that can only tighten Jean's own ([architecture.md](architecture.md#deploying)). *Why:* IT teams run containers; serving what a copy of `app/` serves keeps one way to deploy, and the header is where hard enforcement lives ([enterprise.md](enterprise.md)). *Rejected:* the development server (`scripts/serve.js`, made for 127.0.0.1); nginx's image that runs as root; its full image (60 MB rather than 19, for njs, GeoIP, XSLT, image filters and curl, none of which Jean uses); the gateway under Jean's address (a same-origin GET carries no `Origin`, and behind a proxy that ends HTTPS the gateway can't tell it); the image in `ee/` (it serves the open folder); a policy baked into the image.
- **D320 · D321 · `npm run deploy` puts a commit on a server reached over SSH, as a release switched to at once, after the render package it names is on npm** ([architecture.md](architecture.md#deploying)). *Why:* the shared checkout holds other sessions' unfinished work, and a commit is what was checked; an upload into the served folder would serve two versions' files while it lasts; going back is moving one link; a page saved from the site draws itself with the version the site names, from npm (D305), so a site ahead of npm saves pages that show only their text. *Rejected:* deploying the working tree; publishing after the switch (a page saved meanwhile names a version npm lacks), or going on when publishing fails; an npm token in the environment (a secret, and the account asks for its code to write); rsync into the served folder; a full copy per release (100 MB each, and new ETags, so every file a browser checks again comes back whole); a deploy tool or a CI service; the server's address in the repository.
- **D241 · jean-cli: Jean inside an editor, through ACP, and the gateway in one line** (`cli/`, MIT, published from `dist/cli/` by `npm run cli`). `npx jean-cli acp --folder <folder>` makes Jean the assistant of an editor that speaks ACP, in the folder Sync keeps, so the browser has its conversations after its next round; it works on the editor's folder through the editor, each change and command asked first, with keys from the environment only. `npx jean-cli gateway --origin <address>` runs the gateway (D191). How: [architecture.md](architecture.md#jean-cli). *Why:* power users live in a terminal or an editor; ACP is already the shape of Jean's records and approvals, so one module serves every editor that speaks it. *Rejected:* the name `jean` on npm (a library from 2015, which npm won't transfer since it has a genuine function); a chat of its own in the terminal, and routines run by cron, for now; the bridge as a package (D198: a line from Jean's origin keeps its version matched to the Jean served); serving Jean itself from it (D232: data stays with the address Jean is served from); publishing the root package (`npx` would pull its optional runtimes, about 100 MB); bundling `cli/`; type-checking it with `@types/node`, a dependency of its own, which `bridge/` and `scripts/` go without too.

## Data

- **D11 · D12 · D40 · Data is plain files in OPFS behind `core/fs.js`, written by a storage worker with `createSyncAccessHandle`.** That sets the browser floor: Safari 16.4, Chrome 108, Firefox 111, except for capabilities that need more (D141, D157). *Why:* portable, readable, ready to sync, the user's own; universal beats newest. *Rejected:* Yjs as the data layer; IndexedDB records; `createWritable` on the main thread (Safari 26).
- **D18 · D19 · D82 · D182 · Projects are self-contained folders, called "Project" in the UI:** `projects/<ulid>-<slug>/project.md` beside the project's own conversations, files, instructions, memory, skills and routines ([architecture.md](architecture.md#data-and-persistence)). The header shows the room's project, the address carries it, and its dialog shows who the project is first, Save and Delete apart and always in view ([product.md](product.md#projects)). *Rejected:* "Space", "Agent", "Room" or "Folder"; remembering the last project in settings; tinting the interface's accents; one column of fields with Delete under Save, out of view on a short screen.
- **D228 · Profiles (not built): one device, several Jeans, such as a personal one and a work one.** A profile is a whole Jean: its settings (brains and keys, rules, look, language), its own secrets' key, the person's instructions and memory, its projects, connections, sync places (D227) and routines. Each is a folder, `profiles/<ulid>-<slug>/`, behind a rooted view of the FS that `core/fs.js` gives, so no other module knows of profiles; folder handles and `localStorage` keys are kept per profile, and nothing crosses between profiles (memory, search, @, meetings, Since last time): a project moves by export and import, or through a sync place. The first run makes one, unseen until a second is made, as the home project is; the user's menu lists them and adds one; switching opens the other afresh, as a new version comes in (D138), and an address finds its profile by its task's or project's ULID. A work profile may take an organisation's policy from a signed file or the identity provider's groups, in `ee/`; the open version keeps one `policy.json` per origin. The layout is settled before launch, since data moves only then (D173). *Why:* projects keep their own brains, connections and rules, but the person's memory and instructions go into every prompt, a work brain behind an employer's gateway included; browser profiles separate everything, but few people use them, Chrome on Android has none, and the desktop app is one origin. *Rejected:* accounts on a server; browser profiles alone; profiles as a level above projects that still shares memory and keys; "Account" in the UI, since there is none.
- **D30 · Organisation policy is opt-in,** through `<meta name="app-policy" content="policy.json">`. *Rejected:* always fetching `policy.json` (a 404 for everyone else).
- **D33 · D53 · Every third-party address is a default that settings or policy replace,** resolved when read (`DEFAULT_URLS`, `PROVIDERS` in `core/settings.js`) and never written into `settings.json`. *Why:* "no hard-coded third-party URL" is about services Jean depends on; organisations mirror them. *Rejected:* hard-coding huggingface.co in the workers.
- **D173 · Until the public launch, nothing is kept for earlier versions:** no alias for a renamed tool, no migration of settings or files, no reader for an older shape; a change of shape changes the code and its tests, and the owner's own data follows or starts again. Every file keeps its `format` field, for the lazy upgrades that begin after launch (D11). *Why:* there are no users yet, and each shim cost code, tests and docs for data only the owner had. *Rejected:* keeping the tools a conversation started earlier was given (D46 holds for conversations started from now on).
- **D59 · D137 · D220 · The address holds the place: `#/c/<ulid>`, `#/p/<ulid>/c/<ulid>`, Settings over either, `…/settings/<section>`, and the windows beside it after a `?`,** in the order they opened, so a reload, a link or Back lays them out again ([architecture.md](architecture.md#stack)). Settings adds one history entry, so Back closes it; windows change the entry they are on. *Rejected:* path routing (host rewrites); `#/settings` on its own (loses the conversation underneath); `?settings=` (reaches the server); an entry per section; an entry per window opened (Back would close windows, and walk through a site's own pages); windows as path segments (a state holds slashes); where a site went from the page Jean opened (a framed site's address can't be read, D140); windows kept in settings or storage (the address is what reloads, goes back and is shared).
- **D177 · Settings › Your data breaks the storage down when asked:** What takes up space, under Storage, measures once opened and lists each kind that holds something, largest first, with its size and a bar of its share ([architecture.md](architecture.md#data-and-persistence)). *Why:* a total alone doesn't say what to keep or clear. *Rejected:* Chromium's `usageDetails` (Chromium only, and by storage API rather than by what Jean keeps); a stacked bar with a colour a kind (no palette holds across fifteen themes and forced colours); measuring whenever the section opens (it reads every file's size).
- **D305 · A task saves as a web page that holds its own file, and draws itself as Jean does with a package of Jean's own files.** *Save a copy* writes `<its name>.html`: the conversation's JSONL as it is, the pictures it made, a few lines of its own that show its requests and answers as written, and the render package, `@codename/jean-render`, Jean's own files at the version the page names, each checked by its hash, which draws it as Jean does when it can be reached ([architecture.md](architecture.md#data-and-persistence)). *Why:* one file that opens with a double click anywhere, keeps the whole conversation as Jean wrote it, with its pictures, and looks as it did, without carrying Jean's renderers and their libraries in every copy; offline, it still reads. *Rejected:* a name that says what kind of file it is ("Save as a web page"), which is how, not what; a Word document or Markdown, which keep only the words; the bare `.jsonl`, which nothing opens; the renderers and their libraries in each copy, a megabyte or more for a chart and more for a map; Jean's own site as the package, which a desktop app or a Jean on this computer doesn't have, whose files change under the copies it made and whose address can move; the answers drawn into the file as pictures as it is saved, which a page or a chart's tips can't be, and which says everything twice.
- **D340 · D341 · Restore also brings in what Gemini, ChatGPT and Claude kept, and so does their export shared in the box,** each export known by what it holds rather than its name, and nothing brought in twice ([architecture.md](architecture.md#data-and-persistence)). *Why:* people arrive with years of conversations in another assistant, and these exports are how they get them back; an export's name says nothing (ChatGPT's is a hash, Claude's parts are `data-…`). *Rejected:* a reader for DEVS's own export (D38; DEVS exports in Takeout's layout); Takeout's other format, web pages (dates written in the account's language, a layout no one documents), so the user is told to export again in JSON; a conversation brought in again when it grew since (it is left as it is); what an assistant's tools did and what it thought (searches, code run, ChatGPT's canvases, Claude's artifacts, reasoning), which a Jean answer has no place for as it was; ChatGPT's generated pictures, which its exports dropped, then moved to `library_files.json`, over 2026; putting a Claude conversation in its project (the export doesn't link them).

## Security

- **D28 · Trusted Types is enforced, with one extra policy, `app-urls`,** that allows only same-origin script URLs (the workers). *Rejected:* dropping `require-trusted-types-for`.
- **D29 · Inline code is allowed by hash,** each guarded by `test/html.test.js`: the import map, the first-paint line (D85, D111) and the update's view-transition opt-in (D138). *Rejected:* `'unsafe-inline'`; a bundler.
- **D326 · Every page's policy is checked in every engine, by the browser's own reports:** the development server serves each page's policy again as a report-only header and keeps what browsers report, and a smoke test takes Jean through what each policy guards and fails on any refusal but the two expected ([architecture.md](architecture.md#security)). *Why:* a browser's own report covers Trusted Types and workers made from blobs too, in every engine, with no hook into the page. *Rejected:* a `securitypolicyviolation` listener in each frame (a hook in every document, none in workers, and no Playwright for Safari); the console alone (each engine words it differently, and WebDriver can't read it); `data:` in the sandbox's scripts for Pyodide's question (a looser sandbox for an answer Pyodide does without).
- **D35 · D336 · An answer shows a picture only at the address a source gave, or one the user shared; any other Markdown image is its alt text.** Search and `browse` bring a page's lead picture, or its own, with the source; it shows from the source's own address, never the one written, and heads an option's card in a comparison ([architecture.md](architecture.md#security)). *Why:* an image address is the classic way for injected instructions to leak data, since loading it sends whatever it holds; an address a tool gave holds nothing the brain chose, and loading the source's own copy leaves not even its spelling to carry anything. Products, cars and flats are chosen by eye too; an article's lead picture is the one its editors chose, and reading it through `browse` adds no prompt token. *Rejected:* any https picture (the leak); shared pictures alone (products would have none); Jean fetching pictures itself (most sites refuse other sites' reads); a picture made for the occasion (a product as it isn't); a tool to search pictures, Wikimedia Commons' or another's (a tool line in every request, frozen with the others (D46), and Commons searched by a product's name finds files of other things).
- **D13 · D14 · D65 · D80 · Untrusted code runs in one sandbox: a classic worker started from a blob by `sandbox.html`, framed with `sandbox="allow-scripts"` only,** with no network and nothing but what Jean sends in; its requests go through Jean (D162) ([architecture.md](architecture.md#security)). *Why:* code reaches only what Jean hands it, the same in every host. *Rejected:* running code in a sandboxed frame's document (WebRTC, navigation, a frozen tab); a module worker (refused from `blob:` in an opaque origin); `srcdoc` (inherits `index.html`'s policy); serving the runtimes to the sandbox over the network; a second document for Python.
- **D126 · D143 · D158 · D183 · D229 · D267 · A web page shows in `preview.html`, an opaque frame with `sandbox="allow-scripts allow-forms"`, and five switches say what it may do; a Word, Excel or PowerPoint file is drawn in one as Office draws it, and a workbook's cells change where the user sees them.** The switches are in Settings › Approvals › Web pages (`pages` in policy sets and locks them); the relay deletes WebRTC from the page's window, and saving goes through Jean after a click of the user's. Office files are drawn by `@silurus/ooxml` (MIT) on a canvas, nothing fetched. A cell changed in the preview is a copy the version on show then holds, since files are named by their content and what the brain read stays as it was; in the browser, a workbook of the folder or the workspace changes where it is ([architecture.md](architecture.md#security)). *Why:* the pages Jean makes are charts and small tools that need their scripts, and their forms: Chromium fires a form's `submit`, and closes a dialog by its form, only where forms are allowed, so a page that worked out its sum on Enter did nothing, and `form-action 'none'` in both policies sends none. WebRTC would send what a page holds to any server it names, past every policy, Send and receive off included, and the page's window is the only one it reaches. People judge a deck or a workbook by how it looks, and browsers have no Office of their own: drawing it on the device is the closest to native that keeps the file there, and a canvas puts nothing of the file in a document as markup. ## Desktop

- **D155 · D160 · A desktop app, with Neutralino.** `npm run build:desktop` embeds the files a deploy serves in Neutralino's binary, which serves them on 127.0.0.1:24601 (fixed, since the origin holds the data) to a window of the system's own web view: `Jean.app` (bundle id `is.jean.desktop`), `jean-win_x64.exe` and `jean-linux_*`; `npm run build:dmg` makes the Mac's disk image. None of these come from `BRAND`, and none may change once in use. The native API is on for twelve calls only (`NATIVE` in `scripts/desktop.js`): for Sync's folder (D157), the computer's memory in Settings › Computer (D176), and the two programs the app runs: This computer's bridge, started, listed and ended through its input (D198), and the system's list of the computer's network addresses, read from what it writes (D260); `ui/host.js` takes the one-time key as Jean opens and carries every call, which only it and This computer make. On the Mac, a launcher inserts `libjeanframe.dylib`, which turns on WebKit's internal setting that ignores `X-Frame-Options` and `frame-ancestors`, so sites that refuse frames show in the browser pane (window-wide, so the preview's frames get it too; accepted). That needs bundle mode, since the embedded build's resource reader crashes when an extra library loads; Windows and Linux stay single embedded files. Developer ID signing and notarization will need the `allow-dyld-environment-variables` entitlement. *Why:* the system's web view stays lean, and the window serves exactly what a deploy copies. *Rejected:* Electron; Tauri; Neutralino's random port; its client library; a native bridge beyond what Sync, Settings › Computer and This computer ask; `os.execCommand`, or any program but the bridge and the list of addresses.
