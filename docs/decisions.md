# Decisions

Each entry is a decision as it stands: what was chosen, why, and what was rejected, so it isn't proposed again. Numbers are stable, because code and docs cite them. When a later decision amended an earlier one, both live in one entry under all their numbers, so searching for any `Dnnn` lands on the current rule; git history keeps the original wording. D124 and D151 were never used.

A new decision takes the next number after the highest one here (D173), checked again just before writing, since several sessions may add numbers at once. It goes into the section it belongs to; if it changes an existing entry, rewrite that entry to the new state and add the number to its heading. A budget is raised only by the owner, in a change of its own.

## Product

- **D1 · Reboot from scratch** rather than refactor DEVS. *Why:* no users or years of fixes to protect; cutting 95% is harder than writing ~5k clean lines. *Rejected:* pruning DEVS ([background.md](background.md)).
- **D2 · First user: a non-technical knowledge worker; one job: files in, things out.** *Why:* a sharp job beats an architecture ("swarm") as a pitch. *Rejected:* developers first; generic chat; a separate mode for code.
- **D5 · Progressive discovery, like a game.** Jean starts as one box; a capability's code loads when it is discovered, so the simple first screen and the small first load are one decision. *Rejected:* a feature-complete UI from day one.
- **D6 · Discovery is triggered by events, reflexes and the brain's `offer()`, never by keywords,** so it works in every language. *Rejected:* regex or keyword intent rules.
- **D7 · D224 · D225 · One agent loop, plus helpers, meetings of the projects' assistants, and methods as ready-made skills.** Delegation is one tool (D98). **Meetings** (D224): `meet`, in the projects capability, has the assistants of the room's other projects, or of those named (a part of a name is enough), five at most, speak on a topic in up to three rounds (two by default), three at a time; from the second round each hears the minutes so far, so they answer one another. Each speaker is a hidden `speak` call, a child turn with no tools and one step, told who it is (its name, how to be), its project's instructions, the newest lines of its memory and its eight latest tasks with the start of each one's last answer, never another project's (`caps/projects/meeting.js`); the room's assistant chairs, reads the minutes and tells the user what came of it. A project kept on this device doesn't join when the brain is in the cloud, nor one the brain isn't used in (D194), and the minutes say who was left out and why. A project's memory and tasks are its own, so a meeting asks first, naming its projects; Always allow holds for those projects only (`meet` in settings), so a routine that holds one runs on its own; `speak` refuses a project with no meeting under way, so a script can't reach one. **Methods** (D225): the methods people at work recognise are six ready-made skills, one for each kind of work, after the everyday ones in Jean's directory: Project plan (the critical path, ranges as PERT gives them, phases with a sign-off, or short cycles with a board), Goals and strategy (OKR, Hoshin Kanri, or a plan from analysis to control), Problem solving (8D, A3, DMAIC, PDCA, a root cause analysis for an incident that is over, or 5 Whys alone for a small problem), Improve a process (Kaizen, the bottleneck first as the Theory of Constraints has it, or a redesign), What could go wrong (FMEA or a pre-mortem) and Design something new (the double diamond with design thinking's practices, or DMADV). Each picks the method the situation calls for, keeps to the one the room's instructions name, and asks with `ask_user`, recommending one, when it isn't clear. Their practices are rewritten from DEVS's 38 methodologies, ideas and never files (D38): facts and numbers before causes or plans, nothing blamed on a person, at least three options weighed in a comparison with the pick starred, actions with an owner, a date and a measure, a check before answering, charts where numbers say more (a Pareto, a Gantt, a risk heatmap), the document the method makes as Word or Excel, and a routine for the check-ins. *Why:* 2026's winners are single-loop agents; a project with a name and a way of being is what others call an agent, so people ask for their agents to meet, and a standing status meeting is a routine; a method is steps, which is what a skill is. *Rejected:* DEVS's decomposer, standing teams with roles and persona libraries; methodology templates as modes of the loop; speakers with tools (a meeting reads what each project knows, and acting stays the chair's, under the rules); assistants calling meetings among themselves, or rounds without end; a transcript per meeting; each speaker on its own project's brain (one answer mixing keys and providers); a skill per method (a line each in `<skills>` once added, and tiles nobody can tell apart); a method field in `project.md` (instructions already say it); DEVS's methods for developers (test-driven, behaviour-driven and domain-driven design, XP, the V-model, RAD, Crystal, SAFe, Scrum for software), since Jean's first user doesn't write code (D2); its agent patterns (greeter, operator, orchestrator, listener), the swarm this entry rejects; TQM, a culture rather than steps; Six Sigma apart from DMAIC, its method; YOLO, which is what Jean does without a skill.
- **D27 · D242 · Data is bound to the origin, so the domain is settled before launch: jean.is, bought.** The desktop app's bundle id is its reverse, `is.jean.desktop` (D155). *Why:* changing it means moving everyone's data. *Rejected:* launching on a temporary domain; jean.cx.
- **D38 · D50 · Jean is its own project, in its own repository.** It moved out of DEVS with its history (`git subtree split`): no devs.new redirect, no import from DEVS, nothing read, imported or copied from outside the repository. *Rejected:* Jean as DEVS's successor; a DEVS subfolder.
- **D3 · D39 · D139 · Open core: MIT, with the enterprise integrations in `ee/` under the Elastic License 2.0 and a key.** Reputation first, money second. Everything a person or a team uses is MIT; `ee/` holds only what an organisation's IT, security or compliance team asks for ([enterprise.md](enterprise.md#open-and-enterprise)), never the person's own security, a standard Jean speaks or anything already open, and nothing moves from open to `ee/`. Keys are ES256 JWS from CODENAME SAS, read from policy and checked offline with Web Crypto inside `ee/`; a subscription key unlocks every version released before its end date; a trial key lasts 30 days, bound to the deployment's addresses; `localhost` needs none; small organisations, non-profits and schools get free ones. A policy that asks for `ee/` features without a valid key stops Jean with a message for IT. `ee/GRANT.md`: if no key can be bought for twelve consecutive months, every version published until then is MIT. `ee/` loads with `import()` from one module, only when policy holds a key. *Why:* small players get the whole product, big ones adopt it bottom-up and pay when their IT needs the integrations; Elastic-2.0 is short, on the SPDX list and known to legal teams; Ed25519 would need browsers above D40's floor. *Rejected:* BUSL on everything; AGPL with a commercial licence; FCL (not on the SPDX list); PolyForm Small Business; a custom licence; online key checks; keys that stop a running version; locked features shown in the open version.
- **D45 · D226 · One relay, not built, for what needs browsers to reach each other: live sharing, requests between people's Jeans, and a person's phone driving their Jean (D227).** Hosted by the maintainer on a subdomain of Jean's domain, it runs only once someone turns one of them on, forwards end-to-end-encrypted traffic it can't read, and is self-hosted or switched off by policy (`urls.collaboration`). Two Jeans pair through a link whose `#fragment` carries the key, which never reaches the relay. **Requests between people's Jeans** (D226): my Jean sends a request to a colleague's; it arrives in their decision inbox as a card, read as data and never as instructions; their Jean answers with their own brain, keys and rules, only reading unless they allow more (as Since last time does, D101), and they approve what goes back. A2A's messages are the likely format over the relay, to confirm when it is built. **Live sharing:** WebRTC between the participants, the relay for signalling, a TURN server of the organisation's where a network needs one, and Yjs only for shared documents. Secrets never cross. *Why:* a person's agent is their project, on their device; working with colleagues means asking theirs, and each side keeps its keys and its say. *Rejected:* no public relay; a relay that can read content; a Jean server that runs agents; a request run with the sender's authority; one person's brain answering for another.

## Stack and budgets

- **D9 · D43 · D51 · D52 · D74 · D183 · D185 · D196 · D243 · No build step, nothing generated or third-party is committed, and what a deploy serves is one folder, `app/`.** Plain ES modules and an import map, JSDoc checked by `tsc --noEmit`; Jean's own code ships as written. `npm run dev`, `start`, `build` and `check` copy the three upfront libraries (only the lit-html files Jean imports) and the on-demand runtimes (`optionalDependencies`: pdf.js, Transformers.js with onnxruntime-web, QuickJS with feross's `buffer`, Pyodide, just-bash, `@silurus/ooxml`, Temml, ECharts, abcjs) from Jean's own `node_modules` into `app/vendor/`, rewriting bare specifiers where import maps don't reach (workers), patching what Trusted Types and the CSP refuse (each patch found exactly as often as expected, or the copy stops), and write `capabilities.json`, `manifest.webmanifest` and a copy of the root's `LICENSE` in `app/`. The committed `index.html` preloads and `sw.js`'s `VERSION` line are stamped, and `npm run manifest -- --check` checks them. A runtime is listed under the capabilities that use it, never in the shell, and nothing comes from a CDN (Transformers.js gets `wasmPaths`). **`app/` holds what a deploy serves** (D243): the pages, `brand.js`, `sw.js`, `core/`, `ui/`, `caps/`, `locales/`, `fonts/`, `icons/`, `screenshots/`, `ee/` and the bridge a line of Jean's fetches (D198). The root holds what never ships: `cli/` with its strings (`cli/locales/`), `gateway/`, `desktop/`, `deploy/`, `scripts/`, `test/`, `e2e/`, `docs/` and `prompts/`; paths to Jean's own files in the docs and comments are `app/`'s. Deploying is `npm ci && npm run build`, then copying `app/`. *Why:* view-source is the source; third-party code in history is noise in every diff; `package-lock.json` makes the copies reproducible; one folder to copy, and a root that shows the project rather than the site. *Rejected:* a Vite or TypeScript build; committing `vendor/` or the generated files; runtimes from a CDN; `transformers.min.js` (bundles its own ORT); a monorepo of packages (`packages/core`, `packages/web`…), since a browser loads `core/` from the folder it is served from: a package of its own would be copied in at build, a build step under another name, or reached through `node_modules` links that a copied folder loses, while jean-cli is the app's own modules, which `npm run cli` already puts together; `LICENSE` only in `app/` (forges look for it at the root) or committed twice. Known cost: `npm install` also fetches Transformers.js's Node backends (~300 MB, never shipped).
- **D10 · Custom elements with `@preact/signals-core`, `lit-html` and `marked`'s lexer, the only libraries loaded upfront.** *Why:* standard elements upgrade when their module loads, which *is* progressive discovery, and all of it is CSP-safe. *Rejected:* Preact with htm; VanJS; Alpine (needs `eval`); htmx (needs a server).
- **D66 · QuickJS and Playwright.** `quickjs-emscripten-core` with only the release-sync variant (~600 KB with its wasm), loaded on demand; `@playwright/test` as a dev dependency, run by `npm run e2e` in Chromium and WebKit against the fake brain, apart from `npm run check`. *Rejected:* the `quickjs-emscripten` package with every variant; browsers inside `npm run check`.
- **D37 · Development uses a deterministic fake brain** (`test/fixtures/fake-brain.js`). *Rejected:* testing only against real providers.
- **D62 · Mechanisms live in `core/`, product policy outside it.** `core/decide.js` packs Kev's input, `core/deferred.js` finds tools, `core/search.js` ranks text; which reflex questions are asked (`caps/reflexes/questions.js`) and how Auto picks a brain (`ui/auto.js`) are policy, in pure modules tested under `node --test`, and `scripts/reflexes.js` imports the same questions, so what is measured is what runs.
- **D75 · Shared types live in `core/types.d.ts`,** which never ships and which `lines.core` doesn't count. *Rejected:* a JSDoc-only `types.js` counted as code.
- **D96 · D148 · A module that only one capability, or one part of the UI, uses lives with it.** Extraction is `caps/files/extract.js`, pictures from a provider `caps/computer/picture.js`, the backup zip `caps/backup/archive.js`, the language guesser `ui/language.js`, the page policy `ui/csp.js`; `core/zip.js` stays because several share it. All stay tested under `node --test`. *Why:* the core is the engine you read in an afternoon. *Rejected:* raising `lines.core`.
- **D76 · D94 · D148 · D211 · The first load holds what the first screen draws, and one catalogue.** The desktop app's host (`ui/host.js`, imported as Jean opens on 127.0.0.1 alone, D169), the dialogs (`ui/dialogs.js`), the Anthropic adapter (imported by `core/llm.js` when first needed), the loop and the adapters (with the first message), Auto, and what a message needs on its way (`ui/send.js`: the prompt, what the brain reads of the files, the run and its approvals, cache warming, loaded as the user starts typing) all load when first needed, and stay in the shell's precache for offline use. `useLocale()` fetches only the chosen language's catalogue; the budget counts the largest. *Rejected:* preloading after the first paint; a lexer-only `marked` (its published file can't be tree-shaken).
- **D97 · A language's catalogue comes in parts.** `locales/<lang>.json` holds what the first screen and the conversation show; `locales/dialogs/<lang>.json` what only dialogs show, loaded by `ui/dialogs.js`, which every module that shows a dialog imports; a capability whose strings would weigh on the first load brings its own part, `locales/<id>/<lang>.json`, cached with it (browser, ask, folders, sync, computer). `test/locales.test.js` checks that every string is used, and only where its part is loaded. *Rejected:* trimming sentences; one part per capability for all of them.
- **D86 · D129 · D161 · D171 · D175 · D179 · D186 · D189 · D203 · D204 · D206 · D209 · D213 · D217 · D221 · D231 · D237 · D239 · The app's line budget is 29,000, the first load 102.1 KB, a capability's code 50 KB and a part of a language's catalogue 9 KB.** The owner raised the lines from 10,000 to 15,000 (before 0.5), 20,000 (the looks), 22,000 (the Computer), 22,500 (Sync in the desktop app), 22,600 (formulas), 25,000 (going back to a request, D188), 25,500 (LaTeX drawn as it is written, once This computer, D198, had filled it), 25,550 (skills from GitHub and everyday ready-made skills, D207 and D208, once a search for lines to delete found none dead), 25,650 (Whistle's loader for dictation, D205), 28,000 (questions and approvals that come back after a reload, D212, once a search for lines to delete found none dead), 28,500 (a workbook's cells changed in the preview, D229, once their change in place had left one line) and 29,000 (a workbook's formulas worked out again and its cells changed in the browser, D229, once the room's other work had left 140 lines), a capability's code from 40 KB to 44 KB (the Computer shown in Settings) and 50 KB (Node's own modules in the Computer), the first load from 100 KB to 101 KB (Slides, D200, once main had 6 bytes of it left), 102 KB (the windows in the address, D220, once main had 52 bytes left) and 102.1 KB (a brain out of credits saying so in plain words, once main had 7 bytes left, D239), and a part of a language's catalogue from 8 KB to 9 KB (Flows, D218, once the dialogs' part had 11 bytes left in Russian), each in a change of its own. The core keeps 3,000 lines and the CSS 12 KB. *Rejected each time:* raising it inside the change that needs it; thinning a shipped capability.
- **D244 · The development server checks the budgets after each change.** `npm run dev`, `dev:gateway` and `start` run `scripts/budgets.js --short` as Jean starts, then after each change to `app/`, `cli/` or `budgets.json`, each time in a process of its own, and say every budget over, in a line each on the error stream, until all are met again; as Jean starts, they also name those within 2% of their limit. It still serves. *Why:* every budget had reached its limit, and `npm run check` comes once a feature is built around the room it took. *Rejected:* refusing to serve while one is over (the shared checkout holds other sessions' unfinished work, and a feature is seen before it is trimmed); checking only as it starts (a development server stays up for hours); importing the check into the server (Node keeps the prompt's module as it first read it).
- **D240 · jean-cli keeps to 1,500 lines** (`lines.cli`: `cli/`'s modules, comments and blank lines included, D241). It reuses the core and the capabilities' pure modules as they are, so what it adds is what a host outside the browser needs and no more. *Why:* `lines.app` counts what a browser loads, and the core's budget is full. *Rejected:* counting it in `lines.app`; no limit, as `bridge/` and `gateway/` have none.
- **D232 · A container image, for organisations that deploy with containers** (`deploy/docker/`, MIT). A multi-stage Dockerfile builds with `npm ci --omit=dev --ignore-scripts` and `npm run build`, and copies only `shippedFiles()` into nginx's unprivileged slim image (user 101, port 8080, Jean's files read-only). `index.html` gets `<meta name="app-policy">` and an empty `policy.json` beside it, which the organisation's own replaces as a mounted file; empty, Jean is the open version, and no 404 shows in the console. Every file is sent with `no-cache`, `nosniff` and `frame-ancestors 'self'`, and `CONTENT_SECURITY_POLICY` adds the organisation's own policy, which can only tighten. The gateway is a second target of the same file, off unless asked for, at an address of its own. *Why:* IT teams run containers; serving what a copy of `app/` serves keeps one way to deploy, and the header is where hard enforcement lives ([enterprise.md](enterprise.md)). *Rejected:* the development server (`scripts/serve.js`, made for 127.0.0.1); nginx's image that runs as root; its full image (60 MB rather than 19, for njs, GeoIP, XSLT, image filters and curl, none of which Jean uses); the gateway under Jean's address (a same-origin GET carries no `Origin`, and behind a proxy that ends HTTPS the gateway can't tell it); the image in `ee/` (it serves the open folder); a policy baked into the image.
- **D241 · D243 · jean-cli: Jean inside an editor, through ACP, and the gateway in one line** (`cli/`, MIT, published from `dist/cli/` by `npm run cli`). `npx jean-cli acp --folder <folder>` speaks ACP on its input and output, so an editor that does (Zed, JetBrains, Neovim, Emacs) has Jean as its assistant. Each session is a conversation of Jean's in the folder Sync keeps (refused without its `mirror.json`), in the project whose `folder` is the editor's folder's name or else the home one, so the browser has it after its next round; this computer's `settings.json` there, which a mirror never carries, holds who writes the records, the rules the user's answers set and what they always allow in each folder, never a key. A turn is core's, its updates sent as they are but for Jean's entries for a brain's steps, its notes and an answer's follow-ups, and the editor asks what is asked first. The editor's folder is worked on with the Folders capability's tools, whose definitions both share, read and written through the editor where it lets Jean, so unsaved changes count, each change asked with its diff; commands run in the editor's terminal, each asked first, and never JavaScript or Python, which only the sandbox runs; memory, skills, shared files and earlier conversations work as in the browser, and the editor's services (MCP, a program or an address) are found with `find_tools`. The brain is the one `--brain` names, else the first whose key the environment holds, else the user's Claude Code through a bridge started in the process (D235); keys come from the environment only. `npx jean-cli gateway --origin <address>` runs the gateway (D191), its secrets still in `GATEWAY_CONFIG`; the gateway answers Private Network Access for the origins it serves, so Jean's own address reaches one on this computer. The package is every module `cli/main.js` reaches, copied as written, with its strings, `cli/locales/` (the approvals' names and the brains' errors copied from each catalogue, the rest translated), outside `app/` so the web never ships them (D243), and Jean's two runtime dependencies those modules import. *Why:* power users live in a terminal or an editor; ACP is already the shape of Jean's records and approvals, so one module serves every editor that speaks it. *Rejected:* the name `jean` on npm (a library from 2015, which npm won't transfer since it has a genuine function); a chat of its own in the terminal, and routines run by cron, for now; the bridge as a package (D198 stands: a line from Jean's origin keeps its version matched to the Jean served); serving Jean itself from it (D232: data stays with the address Jean is served from); publishing the root package (`npx` would pull its optional runtimes, about 100 MB); bundling `cli/`; type-checking it with `@types/node`, a dependency of its own, which `bridge/` and `scripts/` go without too.

## Data

- **D11 · D12 · D40 · Data is plain files in OPFS behind `core/fs.js`, written by a storage worker with `createSyncAccessHandle`.** That sets the browser floor: Safari 16.4, Chrome 108, Firefox 111, except for capabilities that need more (D141, D157). *Why:* portable, readable, ready to sync, the user's own; universal beats newest. *Rejected:* Yjs as the data layer; IndexedDB records; `createWritable` on the main thread (Safari 26).
- **D18 · D19 · D82 · D182 · Projects are self-contained folders, called "Project" in the UI.** `projects/<ulid>-<slug>/project.md` (`format`, `name`, `colour`, `createdAt`, `by`; `default` for the home project; `cloud: false` to keep it on this device) beside its own conversations, files, instructions, memory, skills and routines. A project with a name and a way of being is what other products call an agent (D102). The header shows the project the user is in and opens on the others; the address carries it; its colour tints the light (D78). The home project's name is never translated: the UI calls it by its assistant's. Its dialog shows who the project is first, its light as picked, large, beside its name and the colours; then its assistant, once names are found; then where it is kept, a switch for this device and its folder; Save and Delete at its foot, apart and always in view. What a project is, it says only when making one. *Rejected:* "Space", "Agent", "Room" or "Folder"; remembering the last project in settings; tinting the interface's accents; one column of fields with Delete under Save, out of view on a short screen.
- **D228 · Profiles (not built): one device, several Jeans, such as a personal one and a work one.** A profile is a whole Jean: its settings (brains and keys, rules, look, language), its own secrets' key, the person's instructions and memory, its projects, connections, sync places (D227) and routines. Each is a folder, `profiles/<ulid>-<slug>/`, behind a rooted view of the FS that `core/fs.js` gives, so no other module knows of profiles; the first run makes one, unseen until a second is made, as the home project is (D18); folder handles and `localStorage` keys are kept per profile. Nothing crosses between profiles: memory, search, @, meetings (D224), Since last time; a project moves by export and import, or through a sync place. The user's menu at the drawer's foot lists the profiles, each with its name and light, and adds one; switching opens the other afresh, as a new version comes in (D138), and an address finds its profile by its task's or project's ULID. A work profile may take an organisation's policy from a signed file or the identity provider's groups, in `ee/`; the open version keeps one `policy.json` per origin. The layout is settled before launch, since data moves only then (D173). *Why:* projects keep their own brains, connections and rules, but the person's memory and instructions go into every prompt, a work brain behind an employer's gateway included; browser profiles separate everything, but few people use them, Chrome on Android has none, and the desktop app is one origin. *Rejected:* accounts on a server; browser profiles alone; profiles as a level above projects that still shares memory and keys; "Account" in the UI, since there is none.
- **D30 · Organisation policy is opt-in,** through `<meta name="app-policy" content="policy.json">`. *Rejected:* always fetching `policy.json` (a 404 for everyone else).
- **D33 · D53 · Every third-party address is a default that settings or policy replace.** Providers' endpoints (`PROVIDERS`), OpenRouter's sign-in, Wikipedia, the model weights host, the package registries and the site icons (D210) are identities of what the user picked or defaults in `DEFAULT_URLS` (`core/settings.js`), resolved when read, never written into `settings.json`. *Why:* "no hard-coded third-party URL" is about services Jean depends on; organisations mirror them. *Rejected:* hard-coding huggingface.co in the workers.
- **D173 · Until the public launch, nothing is kept for earlier versions.** No alias for a renamed tool, no migration of settings or files, no reader for an older shape: a change of shape changes the code and its tests, and the owner's own data follows or starts again. Every file keeps its `format` field, for the lazy upgrades that begin after launch (D11). *Why:* there are no users yet, and each shim cost code, tests and docs for data only the owner had. *Rejected:* keeping the tools a conversation started earlier was given (D46 holds for conversations started from now on).
- **D59 · D137 · D220 · The address holds the place: `#/c/<ulid>`, `#/p/<ulid>/c/<ulid>`, Settings over either, `…/settings/<section>`, and the windows beside it after a `?`.** Opening Settings adds one history entry, so Back closes it; another section takes the same entry; closed where it opened, it goes back. The windows (the preview, the browser, the terminal, Flows) are each a name and what it shows, in the order they opened, so the dock lays them out again the same way: `?flow=task&terminal&browser=https://example.com/`. Each window's module writes its own state and checks one it is given (`preview=files/<file>`, the browser's address as Jean opened it, `flow=` a flow or `task`); a name Jean doesn't know, or one whose capability isn't found yet, is passed over, so an address stays good as windows come and go. They change the entry they are on rather than adding one. Opening an address, by a reload, a link or Back and Forward to another place, shows its windows; Back and Forward within a place (a site's own pages, Settings closing) leave them as they are; a window shown again doesn't take the keys. The unsent draft is kept per conversation in `sessionStorage`. Other dialogs stay out of the address. *Rejected:* path routing (host rewrites); `#/settings` on its own (loses the conversation underneath); `?settings=` (reaches the server); an entry per section; an entry per window opened (Back would close windows, and walk through a site's own pages); windows as path segments (a state holds slashes); where a site went from the page Jean opened (a framed site's address can't be read, D140); windows kept in settings or storage (the address is what reloads, goes back and is shared).
- **D177 · Settings › Your data breaks the storage down when asked.** "What takes up space", under Storage, measures once opened and lists each kind that holds something, largest first and everything else last, with its size and a bar of its share; the total shown becomes their sum. *Why:* a total alone doesn't say what to keep or clear. *Rejected:* Chromium's `usageDetails` (Chromium only, and by storage API rather than by what Jean keeps); a stacked bar with a colour a kind (no palette holds across fifteen themes and forced colours); measuring whenever the section opens (it reads every file's size).

## Security

- **D28 · Trusted Types is enforced, with one extra policy, `app-urls`,** that allows only same-origin script URLs (the workers). *Rejected:* dropping `require-trusted-types-for`.
- **D29 · Inline code is allowed by hash,** each guarded by `test/html.test.js`: the import map, the first-paint line (D85, D111) and the update's view-transition opt-in (D138). *Rejected:* `'unsafe-inline'`; a bundler.
- **D35 · Markdown images in a brain's answer are never loaded;** only their alt text shows. *Why:* an image address is the classic way for injected instructions to leak data.
- **D13 · D14 · D65 · D80 · Untrusted code runs in one sandbox: a classic worker started from a blob by `sandbox.html`, framed with `sandbox="allow-scripts"` only.** Its CSP is `default-src 'none'; script-src 'sha256-<relay>' blob: 'wasm-unsafe-eval' 'unsafe-eval'; worker-src blob:; connect-src 'none'`. The parent sends every file in (QuickJS, Pyodide and just-bash, as `capabilities.json` lists them); Pyodide's `fetch` serves only those, under an address that never resolves. `'unsafe-eval'` is for Pyodide's start-up, harmless in an opaque origin with no network. QuickJS gets 64 MB and 20 s of computing time (waiting on Jean or the user doesn't count); a watchdog in the parent stops a run that goes quiet. Requests go through Jean (D162). *Why:* code reaches only what Jean hands it, the same in every host. *Rejected:* running code in a sandboxed frame's document (WebRTC, navigation, a frozen tab); a module worker (refused from `blob:` in an opaque origin); `srcdoc` (inherits `index.html`'s policy); serving the runtimes to the sandbox over the network; a second document for Python (until D162).

- **D8 · Short, calm prompts, after pi:** about 200 tokens in sections, one line per tool. *Rejected:* DEVS's 2,000-token personas.

## Desktop

- **D155 · D160 · D169 · D176 · D198 · A desktop app, with Neutralino.** `npm run build:desktop` embeds the files a deploy serves in Neutralino's binary, which serves them on 127.0.0.1:24601 (fixed, since the origin holds the data) to a window of the system's own web view: `Jean.app` (bundle id `is.jean.desktop`), `jean-win_x64.exe` and `jean-linux_*`; `npm run build:dmg` makes the Mac's disk image. None of these come from `BRAND`, and none may change once in use. The native API is on for twelve calls only (`NATIVE` in `scripts/desktop.js`): for Sync's folder (D157), the computer's memory in Settings › Computer (D176), and the one program the app runs, This computer's bridge, started, listed and ended through its input (D198); `ui/host.js` takes the one-time key as Jean opens and carries every call, which only it and This computer make. On the Mac, a launcher inserts `libjeanframe.dylib`, which turns on WebKit's internal setting that ignores `X-Frame-Options` and `frame-ancestors`, so sites that refuse frames show in the browser pane (window-wide, so the preview's frames get it too; accepted). That needs bundle mode, since the embedded build's resource reader crashes when an extra library loads; Windows and Linux stay single embedded files. Developer ID signing and notarization will need the `allow-dyld-environment-variables` entitlement. *Why:* the system's web view stays lean, and the window serves exactly what a deploy copies. *Rejected:* Electron; Tauri; Neutralino's random port; its client library; a native bridge beyond what Sync, Settings › Computer and This computer ask; `os.execCommand`, or any program but the bridge.
