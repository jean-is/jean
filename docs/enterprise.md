# Enterprise readiness and future features

Nothing planned is ruled out by the architecture:

- **Backup and a synced folder** need no server at all.
- **A person's devices, sharing by link and requests between people's Jeans** each need a small server, optional and self-hostable, that keeps or forwards only what it can't read.
- **Enterprise control works the web way:** enforcement comes from the organisation's own hosting, security headers and AI gateway, not from rules inside Jean.

## What it cannot do, by design

These follow from keeping data on the device with no server. Companies already cover them with device management (MDM) and gateways.

- Guarantee anything on unmanaged devices. Rules inside the browser are advisory; real enforcement is the CSP header, network filtering and the gateway.
- Provide an authoritative audit of local actions.
- Let the organisation remotely wipe or revoke data already on a device. A person can remove one of their own devices, which erases Jean there the next time it opens unless they untick it, but a key it held can't be taken back (D700).
- Run scheduled jobs while no tab is open; that would need an optional runner. Routines run while Jean is open, and catch up at the next visit (D122).
- Hold jean-cli to policy (D241). It isn't served from the organisation's address, so it reads none: where Jean must keep to policy, block `npx jean-cli` with the machine's own controls.

The trust pack is open ([trust/](trust/README.md), D419): a threat model, how Jean answers ANSSI's recommendations for generative AI, a DPIA template, how accessibility is checked, an outside penetration test's brief, and releases signed by Warehouse SAS with their bill of materials, to deploy without building. Long-term-support releases, filled-in security questionnaires, the penetration test's report and a copy hosted at the organisation's own address ([Hosted copies](#hosted-copies)) come with a subscription. They are services, not code.

**Promises.** The person's own security is never paid for. Features never move from open to `ee/`; they may move the other way. Without a key, enterprise features don't appear at all, so the unlock game never shows a paywall.

**Keys.**
- Warehouse SAS signs them (JWS, ES256). Jean checks them offline with Web Crypto and reads them from policy (`key`); it never calls home. The check lives in `ee/` (`ee/key.js`): the signature, the origins the key names, and its end against the date this version of `ee/` was released, or against today for a trial.
- A subscription key unlocks every version released before its end date, forever. When a subscription lapses, a running deployment keeps working; only upgrades of `ee/` stop.
- A trial key is free for 30 days, one per address, with no fallback. An organisation asks for it, a free key or a subscription on jean.is's key page (`/enterprise/key`), never by email: the page sends the request to Warehouse SAS, who signs each key by hand where its private half is kept offline and sends it by email. For a subscription, the page makes the quote to print.
- A policy that asks for enterprise features without a valid key stops Jean with a message for IT. Its rules are never dropped silently; removing those sections gives back the open version.
- On `localhost`, no key is needed. An organisation of fewer than 250 people gets a free key.
- One rule prices it (D428): an organisation of 250 people or more pays €9,900 a year excl. VAT, whatever its size, and one that serves Jean to many organisations pays it once. Everything is included: the enterprise features, long-term-support releases, filled-in security questionnaires, the penetration test's report, help to set up, and a hosted copy if wanted. No seats, since Jean can't count them, no tiers and no discounts. Four years stay under France's €60,000 excl. VAT for buying without a tender. jean.is's page for IT says so, at `/enterprise` and `/fr/entreprise`.
- If no key can be bought for twelve consecutive months, every version of `ee/` published until then becomes MIT.

## Hosted copies

An organisation that would rather not serve Jean itself has Warehouse SAS serve its copy, with a subscription or for a trial (D456). How the server does it is in [deploy/](../deploy/README.md#hosted-copies).

- **What is hosted:** files, and nothing else. Every hosted copy is the same release; only its `policy.json`, its `Content-Security-Policy` and, if it is pinned to one, its release are the organisation's. There is no admin console: the policy is the organisation's to write, `policy.html` at its address checks it, and Warehouse SAS puts it up.
- **What never reaches Warehouse SAS:** people's data, which stays on their devices as everywhere else, and their requests to brains, the gateway and connections, which go from the browser to the addresses the policy names; the header keeps Jean to its own files and those addresses. The server sees what any web server sees of a visit, the address asking and the files asked for, and keeps no log of it: [trust/hosted.md](trust/hosted.md) has the detail, and where the server runs. Where the policy names `relay.jean.is` and signs no one in, what goes between a person's devices passes through it sealed: it sees when devices talk, sizes and addresses, never what they say, and keeps each message 7 days at most and the address each change came from a year, sealed (D45, D700).
- **What it can't promise:** the code and the header are whatever Warehouse SAS's server sends. An organisation that must hold those itself serves Jean itself, from a signed release ([trust/releases.md](trust/releases.md)).
- **Its address:** the organisation's own, such as `ai.acme.com`, which it points at Warehouse SAS's server with a CNAME record. A browser keeps each person's data with the address Jean comes from, so an address the organisation owns lets it later move its copy, to its own server or another host, by changing that record, with everyone's data still there. A trial can start at a subdomain of jean.is, such as `acme.jean.is`, but data kept there stays tied to jean.is: leaving means a new address and each person bringing their data over by backup and restore.
- **Its key:** issued for that address. A trial key for `https://acme.jean.is` doesn't unlock `https://ai.acme.com`.

Policy brains are the only brains, chosen among by Auto or by hand, and Settings says they are set by the organisation. `ownBrains` lists the providers whose brains people may keep of their own beside them, `*` any: with `"ownBrains": ["claudecode"]`, someone who pays for Claude keeps it through This computer, and Settings › Brains offers only the ways to those providers, policy's brains locked one by one. A brain of theirs never takes one of policy's ids, and where `jurisdictions` keeps requests within places, only one on this device or this computer stays. What `dlp.brains` names still decides what may read a task holding marked data. `tiers` names the three models Auto steps through for a brain's provider, the least costly first (`"tiers": { "custom": ["small", "medium", "large"] }`), each used only when the gateway lists it: with Intuition on, whose weights come from `urls.modelWeights`, an address the organisation's header must allow, each request goes to the least costly that can do it; without it, to the middle one. A policy brain with `"trains": false`, because the organisation's contract with its service rules out training on what it is sent, may read what Google's services bring in, which goes only to such brains (D440).

Web search is set source by source in `searches`, by the ids `wikipedia`, `vikidia`, `kiwix` (the offline library), `brave`, `tavily`, `google` and `kagi`. `deny` lists those people never have, which Settings doesn't show, and leaves the others theirs to turn on or off; `brain` there refuses the search a brain's provider runs itself, so Wikipedia answers in its place. `on` lists those that are on, every other off, and locks the switches: `{ "on": ["wikipedia", "kiwix"] }` with `urls.kiwix` searches Wikipedia and the organisation's library, nothing else. A search service still needs each person's own key. A connection that searches the web is a connection, kept or hidden in `directory`, and denying the capability `web-search` leaves none of it.

Connect a service lists the services Jean knows. `directory` adds the organisation's own, changes one's address or client id, or hides one (`"hidden": true`). `directoryOnly` turns that list into an allow-list: only the services it names by id, and those `directory` names, show, so a service a new version of Jean knows stays out until IT adds it.

A service's entry in `directory` may also connect it for everyone (`"connected": true`), once Jean reaches it, as policy's `connections` are: the organisation's, locked in each person's Settings › Connections, whose row asks them to sign in the first time (D382). With `{ "id": "microsoft-365", "clientId": "4f1c…", "connected": true }`, everyone has Microsoft 365; signing in at the organisation's own identity provider, Jean names the account its sign-in has, so Entra, its session open, sends the person straight back. Someone who connected it themselves keeps theirs alone. An entry's `scopes` are what its sign-in asks for, those alone, so they list `offline_access` for a refresh token, without which Entra's sign-in lasts an hour, and `openid` and `email` for Settings to show the account. Jean offers only the actions that the scopes the sign-in granted allow. Microsoft 365 asks by default for what a personal account grants too: `User.Read`, which says who signed in, so every list needs it, `Mail.ReadWrite`, `Mail.Send`, `Calendars.ReadWrite` (a Teams meeting's join link with it), `Files.ReadWrite`, `Files.Read.All`, `Contacts.Read` and `People.Read`, with `openid`, `email` and `offline_access`. A work account's go further, each in `scopes` with the rest: `Mail.ReadWrite.Shared` and `Mail.Send.Shared` for the mailboxes shared with the person, `Chat.Read` for Teams' chats, `Team.ReadBasic.All`, `Channel.ReadBasic.All` and `ChannelMessage.Read.All` for its channels, and `OnlineMeetings.Read` with `OnlineMeetingTranscript.Read.All` for what was said in a meeting. Jean's app in Entra lists them all as Microsoft Graph's delegated permissions, and an admin consents once for everyone, since Microsoft's default policy keeps mail, calendars, all files, channels and transcripts from a person's own consent.

The ideas under a new task's box are set in `starters` (D743): each one's `title` and `prompt`, in other languages `title-fr`, `prompt-fr` and so on, as a skill names itself (D222), the language read first, then English, then the plain field, and `skill`, one of Jean's ready-made skills its click brings. They take the place of Jean's four while a person has none of their own; `"only": true` keeps them alone, Settings › Ideas showing them set by the organisation. With `capabilities.preUnlock` holding `starters`, Settings › Ideas is there from the start.

A site Jean makes runs offline in its preview, as on its host, where only its own files reach it. `sites.sources` adds https origins, `*.` for a domain's subdomains, to what its pages take style sheets (`style-src`), pictures (`img-src`) and fonts (`font-src`) from, such as the organisation's own fonts. The share host takes the same in its `HOST_CONFIG` (`sites.sources`), so a site published there looks as it did in Jean.

A policy that signs in, names the brains or holds a key makes the copy an organisation's, where Add a profile makes only grown-ups' profiles: a child's, set by a parent, is for jean.is and copies of one's own (D389).

## Languages and themes

Policy keeps Jean to the languages and themes an organisation supports, and may dress it in its own theme and name.

- **`name`:** what the organisation calls its copy, wherever Jean says its name: the room, Settings, the tab's title, what it says of itself, the files it marks as made by it (D698). A project's own name for its assistant still goes first there. An install takes its name from the manifest, which the browser reads before Jean starts, so it keeps Jean's unless the server names it too, as the container's `APP_NAME` does ([deploy/docker/](../deploy/docker/README.md#configure-it)).
- **`locales`:** the languages offered, by the codes `LOCALES` lists (`"fr"`, `"fr-CA"`, `"zh-Hant"`…). The menu and Settings list only those, and ⌘⇧L and ⌘⌥⇧L go round them. Jean opens in the browser's language among them, else English when listed, else the first; a language the person chose that isn't listed is dropped. One language alone is set, as `"locale": "fr"` sets it, and both say "Set by your organization".
- **`look`:** the organisation's own theme, first in the gallery and the one Jean starts in. Its `logo`, a picture inside the policy (`data:image/…;base64,…`, as a `kit`'s is: Jean takes none from the web), stands beside Jean's name whichever theme the person reads in, on a light plate by night, and is the tab's icon; a mark about as wide as it is tall reads best there. `name` is what the gallery calls it (needed, and not translated); `on` the theme of Jean's it builds on, Tilde unless it names one; then what Make it yours sets: `accent` and `background` as `#rrggbb`, kept readable by night and by day, `size` (0.85 to 1.3 of the browser's text), `font` (`sans`, `serif`, `rounded` or `mono`) and `css`, its own rules over the theme it builds on. Its CSS is written as a person's own is: the starter in Settings › Appearance › Make it yours shows the main hooks, and a rule needs `!important` to win over a theme's. A typeface it names must be served beside `index.html`, since Jean's policy loads fonts from its own address only.
- **`looks`:** the themes of Jean's offered beside it, by their ids (`tilde`, `human`, `mail`, `minimal`, `swiss`, `fjord`, `velvet`, `notebook`, `blueprint`, `classic`, `terminal`, `neon`), in the policy's order; without `look`, the first is the one Jean starts in. `[]` offers none but the organisation's. With one theme offered, nothing switches it: the menu's row and Settings' gallery say it is set by the organisation, and ⌘⇧E does nothing.
- **`kit`:** the organisation's kit (D594, D601): `tokens`, a few flat ones (`paper`, `ink`, `primary` as `#rrggbb` or `rgb()`, `voice`: `calm`, `elegant`, `bold` or `friendly`, `fonts`, `radius`, `dark`) or a design system's in the W3C's Design Tokens format, `layouts`, each a grid of named slots, how its words sit, what paper it is on, the PowerPoint layout it is nearest to and its art, and the `pictures` that art names, as deck's grammar has them (`docs/kits.md` in its package), which drops what fails it. Over Jean's own kit and the person's design system (D602) and under a project's, it is the look of every deck made after, each deck keeping a copy and offered the new one when it changes; its colour and voice are a design's first take's, and those of the Word files and prints Jean makes; its layouts are in the Slide layout menu and in PowerPoint's. `urls.deck` names where a deck's file finds its renderer, jsDelivr's npm mirror unless the organisation serves its own copy of deck's `dist/deck.js`, `{version}` in it the version Jean writes.
- **What stays the person's:** light or dark, which the organisation's CSS styles through `:root[data-theme='light']` and `[data-theme='dark']`, and Make it yours's touches, over the organisation's theme: text size and typeface are how a person reads.

## Signing in at work

Policy's `signIn` names the organisation's identity provider and the app IT registered there for Jean; each policy brain with `"auth": "oidc"`, the organisation's AI gateway, gets its access token as its key, sent as `Authorization: Bearer`, the OpenAI-compatible way, and so does each policy connection with `"auth": "oidc"`, such as the gateway's MCP servers (D385, `caps/signin/`).

- **When:** at the first visit, before the room shows, a curtain going before the trip and greeting the person back by the name the sign-in gave, where their profile has none (D669). With the organisation's session already open, the identity provider sends the person straight back; a shared link opened then comes back to where it pointed. Back from a connection's own sign-in, such as Microsoft 365's, with the organisation's tokens gone, Jean keeps that connection first, then goes.
- **What it asks for:** `openid`, always, and what `signIn.scopes` lists, that alone, written as the identity provider names it, whether its discovery lists it or not: the gateway's scope, and `profile`, `email` and `offline_access` for the person's name, their email and a refresh token, as Entra's below. So a provider that refuses a scope it never granted Jean's app gets only what IT wrote. Without `scopes`, Jean asks for `openid`, and for `profile`, `email` and `offline_access` where the provider's discovery lists them, since some refuse a scope they don't list (Google does `offline_access`); a provider that gives refresh tokens for a scope it doesn't list needs it in `signIn.scopes`. Without `offline_access`, Entra, Okta and Dex give no refresh token, so people sign in again from a toast each time the access token ends; without `profile` and `email`, the ID token names nobody, so neither do the drawer's foot and Settings › Brains, and Sign out stays in the person's menu (D696).
- **Where the tokens live:** in `.secrets/`, sealed at rest, behind the lock when there is one, and never in a backup, export, sync or share; the access token also as each such brain's key. The PKCE verifier waits in the tab's session storage during the sign-in.
- **Renewal:** with the refresh token, half the access token's life before it ends and five minutes at most, so a token of five minutes renews after two and a half, one tab at a time, and when the page shows again. Refused (Entra's refresh tokens for single-page apps last 24 hours), the tokens go and a toast asks to sign in again, keeping what was typed; unreachable, they stay for the next try. A sign-in that comes back refused asks from the same toast, never in a loop.
- **Signing out**, from the person's menu or Settings › Brains, which says who is signed in, signs out at the identity provider too and in every tab of the profile, and locks the profile if it has a lock. Jean comes back to a screen that says so, with Sign in and the other profiles, and that what is kept here stays on this device where no lock keeps it, and goes no further until the person signs in, however it is reopened. Nothing ties a profile to an account: whoever signs in next there gets what it holds.
- **The person's groups:** the ID token's `groups` and `roles`, kept with the tokens for [policy by group](#policy-by-group) (D429).
- **The person's name:** the foot of the drawer shows the name the ID token gives (`profile`), or else its email or login, unless the person set a first name of their own in Settings › About you or the profile has a name.
- **The gateway's MCP servers:** an AI gateway that serves MCP servers, as LiteLLM and Bifrost do, needs no key or sign-in of its own for a connection with `"auth": "oidc"`, when it checks the organisation's token there as for its brains (LiteLLM Enterprise's JWT auth does on `/mcp/`, and so does the custom auth in [examples/enterprise/](../examples/enterprise/README.md), each server open to everyone it admits with `allow_all_keys`); one that takes only its own keys is `"key"`, each person pasting theirs, or `"oauth"`, through its own sign-in. Each address is one connection, and one service to Jean, with one rule for reading and one for acting: LiteLLM's `/mcp/` reaches every server it serves, `/mcp/<group>` a group, and `/<server>/mcp` one, which keeps each server's rules apart and names its host in the audit. Jean can't tell what is behind an address, so Google's servers there aren't kept from brains that may train (D440). The gateway answers Jean's origin with CORS for `Authorization`, `Content-Type`, `Mcp-Protocol-Version`, `Mcp-Method` and `Mcp-Name`, or `"gateway": true` relays to it (D191). A token it refuses shows on the connection's row, whose Sign in goes through the organisation's sign-in again.
- **Colleagues** (D731): with the organisation's own relay listing them, people find each other in Settings › People by a few words of their name or email and send each other tasks, with no meeting. Run the relay with `issuers` in `RELAY_CONFIG`, `[{ "issuer": <signIn.issuer>, "audience": <signIn.clientId> }]`, adding `jwks`, its keys' address, where the discovery's aren't those (Entra, for an app with claims mapping: `…/discovery/v2.0/keys?appid=<client id>`); in the chart, `relay.config.issuers`, which lets the relay reach public addresses over HTTPS for those keys. Then name it in policy (`urls.relay`): People is offered there as anywhere a relay and a share host are named, or on from the start with `capabilities.preUnlock: ["people"]`. Each device lists itself daily with the ID token the sign-in keeps, which the relay checks and drops; it keeps each person's name, email or login, groups and app roles, whether a guest, and each of their devices' mailbox and public key, a device for 30 days after its last proof. Since each letter names its sender's key, which the list holds, the relay can tell who sends to whom among colleagues, never what. For a leaver, `node relay/serve.js forget <account>` (`kubectl exec` in the chart's relay pod) takes them off at once. Someone not on the list yet is invited from the person's own mail app (a `mailto:` link holding Jean's address); once they sign in from it, each has the other. The relay never sends mail. Who may reach whom, policy's `colleagues` says ([Colleagues' controls](#colleagues-controls)).
- **Entra ID**, for IT:
  1. Register an app for Jean as a *Single-page application*, with Jean's address as its redirect URI, which also comes back from signing out. The browser reaches the token endpoint only for such an app.
  2. On the gateway's own app, expose a scope (`api://<gateway-app>/chat`) with v2 access tokens (`accessTokenAcceptedVersion: 2`), and grant Jean's app consent for it. `signIn.scopes` lists it with `openid`, `profile`, `email` and `offline_access`, as the policy above does.
  3. Name the issuer by tenant ID, as the tenant's discovery names it.
  4. Have the gateway check the token: its issuer, its audience (the gateway's app) and the scope, as LiteLLM's JWT auth, Portkey or Azure API Management's `validate-jwt` do. One token has one audience, so the MCP servers that take it are behind the same app.
- **Any other OpenID Connect provider** works the same way: its issuer, Jean's client id, and, where the gateway needs a scope of its own, every scope the sign-in asks for, `offline_access` among them for refresh tokens.

## Policy by group

With a key, or on localhost, `groups` gives the people in a group of the organisation's directory, or holding one of its app roles, a policy of their own (D429, `ee/`). Elsewhere, a policy with `groups` and no key that unlocks this version stops Jean with a message for IT.

```json
"groups": [
  { "id": "5a8e2c41-0b7d-4c1e-9f3a-6d2b8e4f1a07", "name": "Legal", "policy": { "brains": [{ "id": "legal", "provider": "custom", "api": "openai", "baseURL": "https://ai.corp.example/legal/v1", "model": "gpt-5", "label": "Acme AI for Legal", "auth": "oidc" }], "rules": { "share": null } } },
  { "id": "Jean.Engineering", "name": "Engineering", "policy": { "capabilities": { "deny": ["connections"] } } },
  { "id": "interns", "policy": { "capabilities": { "deny": ["computer", "connections", "browser"] }, "instructions": "Ask your mentor before sending anything outside the company." } }
]
```

- **Who is in which:** the organisation's sign-in ([Signing in at work](#signing-in-at-work)) keeps the ID token's `groups` and `roles` with its tokens. A section's `id` is one of their values as the identity provider writes it: in Entra, a group's object id or an app role's value; in Okta or Keycloak, a group's name (Keycloak's full path, `/legal`, unless its mapper says otherwise). `name` is what Settings calls it.
- **How a section applies:** for each the person is in, in the order policy lists them, its `policy` goes over the organisation's as a JSON Merge Patch (RFC 7386). An object merges with what is there, anything else (a list, a text, a number) takes its place, and `null` takes it away. So a list is written whole: Engineering's `deny` above is its whole list, the Computer allowed; Legal's `"share": null` lifts the organisation's rule on sharing for them, each choosing their own. Where two sections set the same thing, the one listed later wins.
- **What a section can't hold:** `signIn`, `key` and `groups`, which say who signs in and so whose sections apply. One that holds them, or that Jean can't read, stops Jean with a message for IT, and `policy.html` says why first: it checks each section's `policy` as it checks policy.
- **When:** at each start, before a profile or settings read policy, from the groups the sign-in last gave. Back from signing in, the tokens are kept first, so a first visit has them. A renewal keeps the groups its ID token gives, for the next start: what has loaded can't unload while the page is open.
- **More groups than a token holds:** past 200, Entra leaves `groups` out of the token and names where Graph lists them instead. Jean can't tell then whose sections apply, so it stops with a message for IT: have the token name only the groups assigned to Jean's app (below).
- **What the person sees:** Settings › Brains, under who is signed in, names the sections that apply, by their `name`. What a section sets is labelled as set by the organisation, as the rest of policy is.
- **Entra ID**, for IT:
  1. In Jean's app registration, *Token configuration › Add groups claim*, with *Groups assigned to the application* (`groupMembershipClaims: "ApplicationGroup"`); then assign those groups to the app in *Enterprise applications › Users and groups* (Entra ID P1), so the token holds those alone and never overflows. Groups synced from Active Directory can be named by `sAMAccountName` instead of their object id.
  2. Or app roles: define them under *App roles* (their values, `Jean.Engineering`), and assign people or groups to them; the ID token's `roles` lists the person's.
- **Other providers:** Okta, a `groups` claim in the ID token, by a filter on Jean's app, with `signIn.scopes` listing `groups` too, where the authorization server ties the claim to that scope; Keycloak, a *Group Membership* mapper named `groups`, added to the ID token. Google's sign-in names no groups, so Google Workspace can't have sections yet.
- **Limits:** like every rule inside the browser, a person with developer tools can change what their tab does. What must hold, the gateway checks in its own token: in Entra, the gateway's app adds the groups claim to its access tokens, which LiteLLM's JWT auth, for one, can map to teams and the brains each may use.

## Audit to OpenTelemetry

With a key, or on localhost, `audit` sends the audit stream to the organisation's collector (D386, `ee/`). Elsewhere, a policy with `audit` and no key that unlocks this version stops Jean with a message for IT.

- **Traces, in OpenTelemetry's GenAI conventions:** one a turn, its `invoke_agent` span holding the conversation's and the project's ids, and, for a routine's run, which routine (`jean.routine.id`) and what set it off (`jean.routine.trigger`: `schedule`, `person` with Run now, or `file`, D421). Under it:
  - a `chat {model}` span for each request to a brain: the provider, the model, the tokens read, written and read from the cache, why it stopped, and its error;
  - an `execute_tool {tool}` span for each call: its id and kind, the connection it reached (`jean.tool.service`, its id, and `server.address`, its host), and `jean.decision`, `jean.decided_by` and `jean.declined` when a rule or the person decided it (D308). A script's or a helper's calls go under theirs;
  - a `use_skill` span for each skill used (D421), with `jean.skill.name` and how, `jean.skill.via`: the brain's `skill` call read its steps (`call`, under the call), the box named it with / (`name`), or a mode of the box follows it (`mode`: Visual answers, a child's Learn it).
- **Removals**, once done, are spans of their own, in no turn. Nothing is sent for what a refusal kept (retention may refuse, D412), nor for any task of a project that stays because one of them was refused:
  - `remove_records` when a task is deleted, alone or with its project (`jean.removed.all` true), or going back to a request leaves records out (false), with the conversation's and the project's ids and how many records went (`jean.records.removed`);
  - `remove_profile` when a profile is removed, with its `jean.profile.id`, so the collector knows whose tasks went with it; how many isn't said, since another profile's tasks can't be read.
- **What is done outside the records**, once done, is a span each, in the turn under way in its task, else in no turn (D421). What was in a task carries the conversation's and the project's ids:
  - `add_skill`, with `jean.skill.name` and `jean.skill.source`: `file` (added in Settings), `made` (saved by the brain with the person), `directory` (Jean's own) or `elsewhere`, with the host it came from and the digest it was checked against (`jean.skill.digest`); `remove_skill`;
  - `add_connection`, with `jean.connection.id`, the host as `server.address` and `jean.connection.auth` (`none`, `key` or `oauth`), not when it is signed in to again; `remove_connection`;
  - `add_routine`, with `jean.routine.id`, `jean.routine.every` or `jean.routine.when`, and `jean.routine.flow` when it runs a flow; `remove_routine`;
  - from an answer's actions: `copy_answer`, `share_answer` (the system's share sheet), `save_answer` (`jean.answer.format`: `html`, `docx` or `csv`) and `print_answer`; `save_file`, a file downloaded from its card or the preview (`jean.file.format`, its extension); `save_task`, a task saved as a web page;
  - `add_share`, a link made, with `jean.share.id`, the host, `jean.share.days`, `jean.share.password` and `jean.share.part` when it holds one answer or picture; `remove_share`;
  - `send_people`, a task or what it made sent to someone met, with `jean.people.kind` (`task`, `item` or `reply`), `jean.people.size` and, for a colleague, `jean.people.to`, their account; `open_people`, what someone sent opened, with `jean.people.from` (D732). Under a pseudonym, those accounts are sealed for the trustee as the person's is, or left out without one.
- **The resource:** `service.name` (`jean`, or `audit.service`), Jean's version, and who acted: by default (`"person": "email"`) `device.id`, `jean.profile.id` (D228), and `user.email` from the sign-in (`user.name` for a login).
- **As a pseudonym** (`"person": "pseudonym"`, D427), for organisations whose works council or staff representatives agree to an audit that names no one:
  - **No `user.*` and no `device.id`.** The device's id is the author of every record, skill and file, so a share, a backup or Sync's folder would tie it to a name.
  - **`jean.profile.id` is the pseudonym:** random, made on the device, in no file that leaves it, and the same in `remove_profile`. A person has one on each device.
  - **With `audit.trustee`**, a P-256 public key as a JWK whose private half whoever the agreement names holds (the works council, the data protection officer, or both together), the resource also carries `jean.user.sealed`: the account as the default would name it (`{"user.email": "…"}`), sealed for them as a compact JWE (RFC 7516, `ECDH-ES` and `A256GCM`, its `kid` the trustee's). Any JOSE tool opens it with the private key; IT, the collector's readers and Jean's makers can't. Without a trustee, nothing in the export ties the pseudonym to a person.
  - **Policy:** a value Jean doesn't know, a trustee without `"person": "pseudonym"`, or one holding its private key (`d`) stops Jean with a message for IT, and policy.html says why first.
  - **What Jean can't hide:** with `"auth": "oidc"`, each batch carries the person's token, so the collector's sign-in sees who sent it; the gateway's log names the person of each request, with its time and tokens, which a `chat` span can be matched to; and the collector sees each batch's IP address. What those keep, and who reads them, is the agreement's. With `content`, what is asked and answered often names people too. Less often, a connection's host or a skill's name may.
  - **For the trustee**, a key pair from any JOSE tool, for example `step crypto jwk create trustee.pub.json trustee.json --kty EC --crv P-256 --use enc`; only `trustee.pub.json` goes in policy.
- **What the person sees:** Settings › Your data says that the organisation receives a record of each request, which brain answered and what it did, and what they add, remove, share or save, with or without what they ask and get, and how it names them: by their account, by this device, or by a random name that only the trustee's key ties to them.
- **Metadata only**, unless `"content": true`: then what was asked and answered, what each brain wrote, its reasoning too, each call's arguments and result, as JSON strings, and an error's words (D427), and the names of the connections and routines added (`jean.connection.title`, `jean.routine.title`). Never a path, which holds a profile's name, nor a whole address, which may hold a key.
- **Credentials:** `"auth": "oidc"` sends the organisation's sign-in's token, which the collector's `oidc` authenticator checks. `"auth"` with its own `scopes`, `issuer` or `clientId` makes a sign-in of its own, at the first visit too. `headers` are fixed, and whoever can open Jean reads them in `policy.json`.
- **A chain that shows tampering (D675):** each span has `jean.audit.chain`, `jean.audit.seq`, `jean.audit.prev` and `jean.audit.hash`, a SHA-256 of itself and the one before; `jean.audit.dropped` says how many were let go on the device before it. Each batch's resource names its last hash, `jean.audit.tip`, signed in `jean.audit.signature` by a P-256 key the browser can't export, whose public half is `jean.audit.key`; a batch sent as the page leaves has none, and the next one's covers it. `node ee/verify.js <file> --keys <file>`, from a release or `app/` here, reads a collector's file, whole or a batch a line, and says what is missing, changed or put in. Hashes alone anyone could make again, so what vouches for a copy is a signature under a key you pinned when you first saw it, as this prints them: with none it says nobody vouches and exits 2, and on a problem it exits 1. Verify before any collector processor that adds to or changes a span, which would show as changed. Spans no signature reaches are counted and prove nothing; the newest spans until a batch signs them, a newest chain removed whole, and the oldest removed, which reads as a copy of a later period, can't be told from what was never sent. It proves what a device sent and that the copy hasn't changed since, not that the device told the truth: the gateway's log stays the authority.
- **Sending:** OTLP/HTTP JSON, in batches every five seconds or of 500, again later while the collector is unreachable or busy, at most 5,000 waiting, and what fits in one request as the page is hidden. The collector allows Jean's origin (`cors.allowed_origins` on its OTLP HTTP receiver). Best effort: the gateway's log stays the authoritative one.

## Data-loss checks

With a key, or on localhost, `dlp` looks on the device for what the organisation calls sensitive (D674, `ee/`). Nothing leaves to be checked, and nothing of what is found is ever told: the audit export hears which detector found something (`found_dlp`, with `jean.dlp.detectors` and `jean.dlp.where`).

- **`detect`:** `card` (Luhn), `iban` (its key), `nir` (a French social security number, its key, Corsica's too), `ssn` (an American one, its shape), `secret` (private keys and access keys by their marks), and `{ "id", "name", "pattern", "flags" }` of the organisation's own, a regular expression Jean runs as it is. **`labels`:** words that mark something, found whole, whatever their case.
- **`brains`:** the brains of policy's that may read a task holding any of it, which is how something marked confidential stays on the on-premises brain. Other brains are refused at each request, saying why, with the picker open; a brain on this computer always may. Left out, any brain may read it, and only what leaves below is checked.
- **`then`:** what a call whose arguments hold it does, when it would reach outside (a service's call, an address opened, a search, a picture or a film asked of its service, a command on the person's computer): `ask` (the default) shows the card saying what it holds; `never` refuses, and the brain reads that the organisation's rules refuse it.
- **Limits:** a browser's rules are advisory ([What it cannot do](#what-it-cannot-do-by-design)). Words only: a picture isn't read, and what is encoded, as base64 or in a zip, isn't found. A person can reword what they send, or copy it out. A share isn't checked: `rules.share: "never"` turns sharing off. Answers aren't checked.

## Masked requests

With a key, or on localhost, `dlp.mask` lets a brain outside `dlp.brains` read a task masked rather than be refused (D681, `ee/`). What policy hides is found on the device and goes as marks like `⟦P7f3a9c⟧`, different in each task, and comes back real, so records, tools, files, memory and approvals keep the real values. Nothing leaves to be checked.

```json
"dlp": { "detect": ["iban"], "labels": ["Confidentiel"], "brains": ["vault"],
  "mask": { "hide": ["email", "phone"], "words": ["Projet Hermès"], "keep": ["Warehouse"], "pictures": "hold" } }
```

- **What's hidden:** everything in `detect` and policy's patterns; **`hide`:** `person`, `email`, `phone`; **`words`:** names and terms of the organisation's, whole, whatever their case, also as code and addresses escape them. A person can add a word from under an answer, never take one away. Without `brains`, every brain in the cloud reads masked; a brain on this computer, or in `brains`, reads as it is.
- **`person`:** people's names, read on the device by a small model (`hackshare/curtain-privacy`, MIT, 63 MB once, from `urls.modelWeights`, so a mirror serves it, about 1 GB in the tab while it reads and freed a minute after). Measured on 120 written documents (`npm run masks`, [results](../test/masks/results.md)), with recall at least 97% in English, French, German and Spanish. It isn't measured in other Latin-script languages. It finds next to nothing in other scripts, so a word or a run in one is hidden whole, and a text mostly in one isn't sent, for as long as a task holds it: a person writing in Arabic or Japanese can't reach a cloud brain under this setting, so choose a brain in `brains`, or leave `person` out. It doesn't run on phones or tablets, where a step that needs it is refused. Each word of a name it is sure of is looked for on its own, with its capital, so `Madame Durand` is hidden once `Marie Durand` has been seen, and `Larry Page` doesn't hide every `page`; a word it is less sure of is hidden only where it was found. Organisations and places aren't read: name them in `words`.
- **`keep`:** what stays, the assistant's name always, which the prompt holds.
- **`labels`:** still refused under `brains`: a label marks the whole of a document, and hiding names in it doesn't change that.
- **`pictures`:** `hold` (the default) keeps pictures and scanned pages on the device, as they can't be read for what to hide, and refuses a picture or a film made from a file; `send` sends them as they are.
- **What leaves:** a call whose arguments hold a value known to be hidden, or found by `detect`, `hide` or `words`, and would leave the device, asks whatever Always allow said, and the card says what it would send; `then: "never"` refuses it. So does code on the Computer that holds one, unless its internet is off: a site it lists goes without a card of its own, and a new site's card says what may go with it. Turn the Computer's internet off in policy and data work with hidden values asks nothing.
- **How it's found:** each text is read as a person reads it: decoded from addresses, HTML and code's escapes, its case, accents and kinds of space and hyphen set aside, its digits in any script. So `MARIE-DUPONT`, `Marie\u00a0Dupont` and `Herm%C3%A8s` are the values they are, and each spelling comes back as the one first seen.
- **In code:** a value is escaped for where it lands. A call is refused, and the brain told why, if a mark stands where a value could run as code or end the text it is in: inside arithmetic, a regular expression or backquotes, a value with a line break in a heredoc, or anything but plain words through what runs text as code (`bash -c`, `eval`, `python -c`).
- **When it can't:** what can't be masked isn't sent. A last look over everything about to go refuses the step if anything it knows is still there, however encoded. Only what the brain itself wrote goes back to it as its thinking (`raw`).
- **What the person sees:** under each answer, what the brain didn't see and what it read last; in Settings › Your data, that this isn't anonymous. The audit export hears how many of each kind (`masked_dlp`, with `jean.dlp.kinds` and `jean.dlp.count`), never what.
- **Limits:** masked isn't anonymous. The rest of a text can still say who it is, a value in no list and no pattern goes as it is, and a name the model misses goes as it is, an initial beside a surname (`R. Keller`) most often. Spelled otherwise (reversed, abbreviated, inflected, transliterated, a number split over lines or a private key without its first line), or spread over two texts, a value isn't found, and code on the Computer could print it so. A word that ends a line and starts a value is hidden there, as it may be a value cut short. A tool named after a hidden word stops every request until it is renamed, as a name can't be masked. A word the model takes for a name is hidden though it isn't one, about 1 to 2% of ordinary words on the measured documents. Reading takes a few seconds per ten pages on a recent computer and is estimated at 20 to 40 on an office laptop, which hasn't been tried; the latest 2,000 readings are kept in `.cache/`, by each text's hash, sealed like any file and in no backup or Sync. A brain can't research a name it can't see, and its own web search gets the mark, which the activity shows as it is. Amounts and dates stay readable unless a pattern hides them. A link in an answer carries what's in it when clicked. Gendered languages may agree wrongly. `jean-cli` runs no hooks. A browser's rules stay advisory ([What it cannot do](#what-it-cannot-do-by-design)).

## Sessions

With a key, or on localhost, `session` sets what happens on shared and unattended computers (D676, `ee/`).

- **`idle`:** an ISO 8601 time (`"PT15M"`). With nothing done in any tab for that long, and Jean not at work, every tab locks; with no lock on, Jean signs out. So it needs `"lock": "required"` or `signIn`.
- **`signOut: "wipe"`:** needs `signIn`. Signing out says what it will do and asks, then erases this profile from the device, its files, keys, sign-ins and what the browser keeps for it, and goes on to the identity provider's sign-out. The next person signs in to a new profile; other profiles stay. Copies outside it (a backup, Sync's folder, the person's own folders) stay too.
- **What can't go together:** a wipe with `retention`, which must keep what it erases; idle with a wipe, unless `"lock": "required"`, since a moment away never erases anything. policy.html says so, and a policy that asks for it stops Jean with a message for IT.

## Retention

With a key, or on localhost, `retention` keeps each task's records, and with them its answers' certificates, at least as long as the period it names (D412, `ee/`): an ISO 8601 duration, `"P6M"` for the AI Act's six months (Arts. 19, 26(6)), or `"P1Y"`, `"P90D"`. Elsewhere, a policy with `retention` and no key that unlocks this version stops Jean with a message for IT, as does a period Jean can't read.

- **What is kept:** what leaves a task for good, counted from each record's own time: a task deleted, alone or with its project, and what asking a request again leaves out, here or, once a Sync round brings it, on another device or in the folder itself. Records already older than the period go as they would. Shared files stay or go with their project.
- **Where:** `.kept/<task's id>.jsonl` in the profile's folder, out of sight and sealed at rest like every file (D371). It is a conversation file of its own, only ever added to: the task's header, then each removal's note (when, which device, from which task, how many records, whether the whole task went) before its records. A backup carries it, readable like the rest of a backup, so a backup is how a copy is handed over. Sync's folder doesn't: each device keeps its own copies, of what was removed there and of what a round took from it.
- **When it goes:** at a start, once the last thing added to a copy has been kept its period. The tasks the person keeps are never removed.
- **When nothing goes:** if a copy can't be made (the device's storage is full), the removal is refused and a toast says so; one a Sync round brings stays on this device, and each round tries it again. A profile can't be removed, since this profile can't read another's sealed tasks to keep them.
- **What the person sees:** Settings › Your data says the organisation keeps each task, with its certificates, for at least the period, and that what they delete stays on the device until then, out of sight.
- **Limits:** best effort, like any rule inside a browser: clearing the site's data, or losing the device, takes the copies too. The collector's log (D386, with `content`) and the gateway's stay the authoritative ones.

## The organisation's seal

With a key, or on localhost, `seal` has the organisation's authority certify the key this device seals certificates with (D434), or has a qualified provider seal them with the organisation's own (D436), and `trust` names the authorities whose word the checks take (`ee/`). Elsewhere, a policy with either and no key that unlocks this version stops Jean with a message for IT, as does a part Jean can't read; `policy.html` says why first.

```json
"seal": { "est": "https://ca.corp.example/.well-known/est", "auth": "oidc" },
"trust": ["-----BEGIN CERTIFICATE-----\nMIIB…\n-----END CERTIFICATE-----"]
```

```json
"trust": [{ "lotl": "https://ec.europa.eu/tools/lotl/eu-lotl.xml", "signers": ["-----BEGIN CERTIFICATE-----\nMIII…\n-----END CERTIFICATE-----", "…"] }]
```

```json
"seal": { "csc": "https://sign.corp.example/csc/v2", "credential": "corp-seal", "auth": "oidc" }
```

- **Enrolment:** at a start, when no certificate from that service is kept for the device's key, or the one kept ends within a month, Jean sends the organisation's EST service (RFC 7030) a PKCS#10 request for that key, signed by it, at `simpleenroll`, in base64 lines of 64, as libest needs; the key never leaves the device. The certificate comes back with its chain, or the chain comes from `cacerts`. The authority's profile decides what it certifies, the subject first. `auth` says how the service knows who asks: `oidc`, the organisation's sign-in's token ([Signing in at work](#signing-in-at-work)); `tls`, what the browser holds for it, such as a client certificate a managed browser presents, the service then allowing Jean's origin with credentials; left out, nothing. The service answers Jean's origin with CORS, or the gateway reaches it, its host in `hosts`.
- **Kept:** in `.secrets/`, which no backup, export, sync or share holds, since it names a key that never leaves this device. Settings › Your data names the authority, and until when.
- **A qualified seal:** with `csc`, the base address of a qualified trust service provider's Cloud Signature Consortium API (v2), or of the organisation's proxy to it, and `credential`, the credentialID of the organisation's seal there, the provider seals in place of the device. At each start, `credentials/info` gives the credential's certificate and chain. Each certificate, or picture, is then a SHA-256 Jean computes of what it signs, granted by `credentials/authorize` (its SAD) and signed by `signatures/signHash` (ECDSA with SHA-256), checked against the credential's key before it is kept; the certificate's issuer is that key's thumbprint. Only an ECDSA P-256 key is taken, since certificates are ES256, and only a credential the provider authorizes itself (`implicit`): one that asks a person for a PIN, a code or a sign-in at each signature can't seal unattended. Jean refuses others with the reason in the console, and the device seals meanwhile, a toast saying so. `auth` works as for EST: with `oidc`, each request carries the organisation's sign-in's token, so the proxy, or a provider that accepts the organisation's tokens, knows who asks; no client secret is ever in `policy.json`, and the gateway only relays to a provider that doesn't answer browsers, its host in `hosts`. Settings › Your data names the provider's authority, and until when.
- **Sealing:** a certificate's `x5c` holds the authority's certificate, or the provider's, and the chain above it but its root, and so does a picture's Content Credentials. Once the witnesses dated it (D276), a certificate gets JAdES B-LT's validation data in its unsigned header: the chain in `xVals`, and in `rVals` what each authority said of its certificate then, an OCSP answer from the responder the certificate names, else its CRL, for the witnesses' certificates too, which their tokens carry; an authority a token leaves out comes from the CA Issuers address the certificate below it names, kept in `xVals` once it is shown to have issued that certificate. EU DSS reads it as B-LT when each of those certificates names where to ask, so policy names a witness whose certificates do (`urls.timestamp`), such as a qualified one from the EU's trusted list: with Sigstore's, the default, it stays B-T. The authority's profile also names its CA certificate (CA Issuers) in each certificate it issues, which DSS warns of otherwise. Responders and CRLs mostly answer plain HTTP, which a page served over HTTPS can't reach: the gateway relays to an origin its `hosts` names whole, `"http://ocsp.corp.example"`, the witnesses' responders and CA Issuers addresses included, what they answer being signed. An authority that can't be reached leaves the device's own certificate, and a toast says so.
- **Checking:** with `trust` (PEM, or base64 DER), the check page served beside this policy and `check_certificate` say whether one of those authorities vouches for a seal: its chain leads, each certificate an authority's and valid when it sealed, to one of them; and whether what the certificate keeps shows each unrevoked then, by an OCSP answer the issuer or a responder it certified signed, or the issuer's CRL. The card says so in a line, with the authority's name: certified by an authority the organisation trusts, the same with no proof it wasn't revoked, not certified by one, or revoked before it sealed. When one vouches and shows it unrevoked, and the seal's certificate says it is an EU qualified certificate for seals whose key a qualified device keeps (ETSI EN 319 412-5's QCStatements: QcCompliance, QcType eseal and QcSSCD, with no QcCClegislation naming another country's law), the line adds that it is a qualified seal under EU law (D437). Those statements count only beneath an anchor: anyone can write them into a certificate of their own.
- **The EU's trusted lists** (D439): an item of `trust` may name the List of Trusted Lists, `lotl`, with in `signers` the certificates the Official Journal publishes for signing it (today OJ C/2026/1944's six). Jean takes the LOTL once one of their keys signed it, or a key its pivots announce in turn, each pivot issued after the newest of those certificates and signed by a key the one before announced; then, for each seal, the list of each country its certificates' names give, once a key the LOTL names for that list signed it. Their XML signatures are checked as XMLDSig with exclusive canonicalization, each signer valid when its list was issued. A list's qualified authorities for certificates (CA/QC) are anchors for a seal made while their status was granted, from each one's history; where a list says what an authority certifies for, seals must be among it (ForeSeals) for the card to say qualified. So whoever relays the lists can withhold them, never choose them. The LOTL's host and the lists' don't answer browsers: the gateway policy names (`urls.gateway`) reaches them, `ec.europa.eu` and each list's host (the LOTL's `TSLLocation`s) in its `hosts`, Slovakia's named whole, `"http://tl.nbu.gov.sk"`, its list being plain HTTP. They are read off the page, in a worker, one country's list at a time (Germany's is 5.4 MB, all of them 27 MB), and kept in `.cache/lists/` a day, or read again for a seal made after they were read, which they can't speak for; the check page keeps them while it is open. Where a list that may hold a seal's authority can't be read or checked, the card says nothing of trust rather than that none vouches, and the console says why. The OJ prints each certificate's SHA-256 beside it: check them, since its HTML drops a line of the second; the LOTL's own pointer, whose `TSLType` is `EUlistofthelists`, carries the same six, and EU DSS's demonstration bundle ships them too.
- **Limits:** a seal under the organisation's certificate is attributable to it; a qualified seal, which the EU's law presumes intact and of correct origin (eIDAS Art. 35(2)), needs a key in a certified device, which a browser's isn't, hence `csc` ([certificates.md](certificates.md)). Each certificate or picture sealed is one signature at the provider. The check page judges a qualified seal by `trust`: the provider's root, or the EU's trusted lists. Of a list, Jean reads an authority's statuses and what it certifies for, not its qualifiers (`Qualifications`), which in a few lists say a certificate is or isn't qualified whatever it says itself; EU DSS reads them. A renewal is a new enrolment, since a browser can't present a Web Crypto key as a TLS client certificate (`simplereenroll`).

## Colleagues' controls

With a key, or on localhost, `colleagues` says who may reach whom among the colleagues the organisation's relay lists ([Signing in at work](#signing-in-at-work), D731), and each person's Jean holds it at every step of People (D732, `ee/`): before a meeting, before someone is found in Settings › People, kept, sent to or heard, and before the device lists itself. Elsewhere, a policy with it and no key that unlocks this version stops Jean with a message for IT; `policy.html` says why first.

```json
"seal": { "est": "https://ca.corp.example/.well-known/est", "auth": "oidc" },
"trust": ["-----BEGIN CERTIFICATE-----\nMIIB…\n-----END CERTIFICATE-----"],
"colleagues": { "certify": true, "apart": [["5a8e2c41-0b7d-4c1e-9f3a-6d2b8e4f1a07", "Jean.Research"]], "guests": "refuse" }
```

- **`certify`:** the EST service that certifies the seal ([above](#the-organisations-seal)) also certifies each profile's key, for the account the sign-in names, the email or else the login, as its `rfc822Name`: asked for as the device lists itself, by a PKCS#10 request for an agreeing key (`keyUsage` `keyAgreement`) that the profile key signs, its one signature, and again a month before it ends. The authority's profile must take that account from who asks (`seal.auth`), never from the request alone. The chain goes with each listing, and a colleague's device is found, kept, sent to and heard only while its certificate names their account and their key and leads, each certificate valid, to one of `trust`'s anchors: so the relay can't list a key of its own under a colleague's name. Revocation isn't asked: a leaver goes off the list (`forget`).
- **`apart`:** sets of groups and app roles, as the ID token names them (as for [policy by group](#policy-by-group)), whose people neither find nor reach each other: each in another group of one set. Both ends refuse, so what someone kept apart sends isn't kept. The relay lists each person's groups and roles from their token, by the claim `issuers[].groups` names; someone whose token had more than it holds (Entra's overage) is kept apart from everyone, and so is the person when theirs did. A token that names no groups leaves its person in none.
- **`guests: "refuse"`:** nobody the list calls a guest (`issuers[].guest`, or Entra's `acct` of 1) is found or reached. Without it, People says Guest account beside them.
- **`inside: true`:** people come from the list alone, with no Add a person and no invitation by a code or a link. `apart` and `certify` have it too, since a meeting gives no account, groups or certificate.
- **The audit:** a task sent to a colleague, or opened from one, names their account in `jean.people.to` or `jean.people.from`, as the person is named ([Audit to OpenTelemetry](#audit-to-opentelemetry)): sealed for the trustee under a pseudonym, or left out without one.
- **Limits:** each person's Jean holds these, as it holds policy; the relay lists and finds whomever the sign-in names. A person with developer tools can change what their own tab does, never what a colleague's Jean refuses.

## Data residency

With a key, or on localhost, `jurisdictions` keeps requests to brains within the places it lists (D434, `ee/`): ISO 3166 codes, a country (`FR`), a subdivision (`US-CA`), or `EU` for its member states.

```json
"brains": [{ "id": "corp", "provider": "custom", "api": "openai", "baseURL": "https://ai.corp.example/v1", "model": "mistral-large", "jurisdiction": "FR", "auth": "oidc" }],
"jurisdictions": ["EU"]
```

- **Which brains:** policy's own, which are the only brains once policy names them but those on this device or this computer that `ownBrains` leaves people, each declaring its `jurisdiction`. Jean keeps those within the places, and the brains on this device or this computer, and leaves out the rest before a profile or settings read policy, after a group's sections (D429), which may name places of their own. A brain's own settings can't declare its place: the person writes them.
- **Checked:** `policy.html` names the brains its places would leave out. A policy with `jurisdictions` and no `brains` stops Jean with a message for IT, since the person's own brains would go anywhere.
- **What the person sees:** Settings › Brains says where requests to brains stay, and each answer's certificate names its brain's jurisdiction (D274). Pictures and films are made by those same brains' providers.
- **Limits:** a jurisdiction is the organisation's word for its gateway or provider, which decides where a request goes from there. Connections and web search reach the services they name.

## Decide now (cheap now, expensive later)

1. **A file layout that survives sync:**
   - One file per entity, named by ULID and never renamed.
   - Conversations are append-only JSONL.
   - Attachments are named by content hash.
   - No central index of record.
   - Every file carries a `format` version.
2. **One storage interface (`core/fs.js`) as the only way to reach data.** OPFS now, a real folder next, and drives, WebDAV or remoteStorage later. Sync then means mirroring two back-ends.
3. **`author` and timestamps on every entity,** using a device ID for now.
4. **Settings resolve as defaults ← user ← policy** from day one.
5. **No hard-coded third-party URL.**
6. **An event stream in the core (ACP)** that other parts can subscribe to.
7. **The built-in CSP is the ceiling.** Organisations only tighten it with headers.
8. **Choose the domain before the public launch.** Data is bound to the origin, not the brand. A domain move, or moving people to a self-hosted copy, means export/import or a one-time hand-over page.
9. **Offer backup early.** Safari may wipe a site's storage after 7 days without a visit unless it is installed, and users clear site data themselves.
10. **Profiles' data layout** (D228): several Jeans on one device each live in a folder of their own, settled before launch, since data moves only then (D173).
